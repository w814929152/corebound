## 肉盾塔 Bulwark 玩法② 诊断定稿（Q-T11 顺序2 · 涌现策略 + ①理想肉盾建模）

### 背景

关键设计分叉：肉盾塔"低DPS×高HP"身份从何而来？调研发现塔 DPS=`TowerDPS×h^0.6`、HP=`HP0×h^0.6` 都 ∝ h^0.6 正相关，无法天然造出低DPS坦克。
用户「按推荐」= 涌现策略（零新代码，金标本零改动）：肉盾=玩家把塔放暴露位吸引仇恨，机制已由仇恨支持。

### 关键发现
- 肉盾塔**机制已存在**：仇恨 `_nearest_exposed_tower` 选最近未 Disabled 塔 → 暴露位塔先挨打；怪物锁定后转 AggroTower 停下（冻结 t_remain、不前进、不漏怪）→ 锁仇恨保后排

## ⑤ Sapper 精英玩法⑤ 诊断定稿（Q-T11 顺序3 · 「锁定增伤流」）

### 背景
用户「推进」⑤ Sapper 精英。GDD 设计：Elite 波（每5波）里的一种精英怪，**无视路径直奔最近的塔并攻击（或对塔伤害×3）**，把塔死亡从"随机运气"变成"可预判的决策点"。
机制调研：现有仇恨 `_nearest_exposed_tower` 选"最近未 Disabled 塔 ≤AGGRO_R"、怪锁定后转 AggroTower 停下（冻结 t_remain、不漏怪）。Sapper 与现有仇恨的差异 = ①无视距离门槛 ②对塔×3。

### 用户拍板（AskUserQuestion 三选一）
- 攻塔行为：**锁定增伤流**（复用现有 AggroTower 仇恨态，不新增移动代码，最贴 GDD「或对塔伤害×3」分支）
- 触发/开关：绑定 Elite 波（复用 elite_waves_enabled 开关，MVP 恒 false）
- 锁塔范围：无视距离强制锁（Sapper 出生即锁全局最近塔，不论是否在 AGGRO_R 内）

### 实现（金标本零改动，elite_waves_enabled 默认 false）
- `monster.gd`：新增 `var sapper: bool = false`（setup 默认 false）
- `monster_data.gd`：新增 `const SAPPER_DMG_MULT := 3.0`
- `wave_director.gd`（实时）：`_spawn_one` Elite 波标记 `m.sapper`；`_apply_aggro` 对 sapper 走 `_nearest_tower_any`（无视距离）；`_aggro_target_valid` sapper committed（不因距离退出）；`_damage_tower` ×3；snapshot 加 `sapper` 字段供 UI
- `wave_sim_aggro.gd`（批处理镜像）：怪物结构扩 `[hp,tr,state,target,m_dps,sapper]`；新增 `_build_sapper_flags`（Elite 波 elite_indices 铺开）；`_apply_aggro`/`_damage_tower`/`_aggro_target_valid` 镜像实时版
- `run_loop_aggro.gd`：run/takeoff_rate 贯穿 sapper
- `tests/scan_sapper.gd`：新建 300 局四组对照（A/B × 有/无 Sapper）

### 🔴 踩坑（两处，均已被单测抓出）
1. **`bool()` 构造器坑**：headless 下 `bool(数组Variant元素)` 报 "Nonexistent 'bool' constructor"。改用 `== true` 比较运算（不触发构造器）。此坑连带把之前通过的 bulwark 批处理测试也弄挂了。
2. **实时 Sapper 永不出生的 gating bug**：初版把 sapper 挂在 `elite`（`_elite_flags[idx]`）上，但 MVP `prototype_split_enabled=false` → elite 恒 false → sapper 永不出。批处理镜像用 `is_elite_wave` 直接判 → 实时/批处理发散。修复：实时版改为直接判 `elite_waves_enabled and is_elite_wave(w)`（不依赖 elite）。
3. **测试时序坑**：`snapshot()` 在 `start_wave` 后立即调 → monsters=[] 测不到（怪随时间出生）。改用 `_advance_until_sapper` 真正推进子步。×3 测试"通过"是假的（两边都 0）。

### 300 局权威数字（决定性，seed=20261002）
- A 无 Sapper = **0.393** / A 有 Sapper = **0.400** → **Δ(A) = +0.007**
- B 无 Sapper = **0.883** / B 有 Sapper = **0.857** → **Δ(B) = −0.027**
- 塔死存量：A 均 1.2 / B 均 0.0

### 定稿结论
- **Sapper 惩罚温和**（Δ 均在 MC 噪声内 ≈ 中性，远优于 −0.10 红线）→ ×3 增伤不过猛、玩法成立、**定稿数值零改动**

- Sapper 是"可读的塔死亡节奏标点"而非崩盘源；可读性靠 Elite 波预警 + 暴露度 UI（玩法①）→ 玩家预判保塔

## ③ 献祭 Salvage Rite 玩法③ 诊断定稿（Q-T11 顺序4 · StackCap+ 增益 · 收益∝投入）

### 背景
用户「推进」③ 献祭。设计：安全窗拆塔第二出口（与回收二选一）——返还 0%+卡销毁+塔位释放，换一次性增益。
用户拍板（AskUserQuestion）：增益形式=**StackCap+**（三选一，耦合单核流）；防刷=**收益∝投入**天然设限（无需计数闸）。

### 实现（金标本零改动）
- `player_state.gd`：新增 `var stackcap_bonus: float = 0.0`（本局累积献祭 StackCap+）
- `damage_engine.gd`：caps 循环后读 `player.stackcap_bonus` 加到每塔 cap（bonus=0 金标本零改动，逐位不变）
- `shop_runtime.gd`：新增 `salvage_rite(slot)`（安全窗校验→卡全销毁→塔释放→返还0%→`stackcap_bonus += floor(invested/10)`）+ `preview_rite` 只读预览 + `RITE_STACKCAP_DIVISOR=10.0`
- `run_loop_aggro.gd`：run() 加 `rite_bonus` 参数贯穿（模拟玩家献祭累积）
- `tests/scan_rite.gd`：300局扫 stackcap_bonus∈{0,5,10,15,25}×A/B
- `tests/probe_rite.gd`：StackCap+ DPS 效应探针

### 🔴 关键发现：StackCap+ 是"突破软顶"型增益（探针实测）
- `reinf_cap=100` 极高 → 只有单塔同 Tag 层数 **>100（进 softcap 衰减段）** 时 cap 才咬合
- 探针数字：lv≤100 时 bonus=10/25 → **+0.00%**；lv=120 时 bonus=10 → **+93% DPS**、bonus=25 → **+272%**
- 金标本 AI 摊层数、从不把单塔堆到 100+ → scan_rite 扫参 bonus 0→25 起飞率**恒定**（A 0.393/B 0.883）
- 🔴 这不是 bug：金标本零改动测试以 152.977/81963705.323 逐位通过，接线正确
- 结论：献祭 = **"极限单核承诺奖励"**——只有玩家主动把单塔堆到衰减段（100+层）才吃得到，一旦生效增幅巨大。主题自洽（沉没成本砸穿软顶，P2 earned + P3 时机），天然防刷（收益∝投入，无新引擎）。平衡性须由玩家策略验证，非金标本 AI 可覆盖。

### 用户拍板：保留 StackCap+（承认条件型增益）
