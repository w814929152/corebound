### 3.3 测试漏洞逐条

#### ① 🔴 T-A′ 裕度不足 + 统计量选错（最严重）

**(i) 裕度：只有 12.5%，置信下界已破线。**
我在 60 局下复跑扫参器，11 个点的 A成型 取值为：

```
ATTRITION : 1.00   1.50   2.00   2.50   3.00   3.50   4.00   4.50   5.00   5.50   6.00
A成型     : 1.000  1.117  1.283  1.083  1.400  1.483  1.067  1.250  1.467  1.467  1.467
```

A成型 对 `ATTRITION` 理论上应单调不减，但实测在 3.5→4.0 出现 **1.483 → 1.067 的 −0.416 逆跳**，即 n=60 下的采样噪声量级约 **±0.2**。据此：

- SE(60) ≈ 0.15 ~ 0.20 → **SE(300) ≈ 0.07 ~ 0.09**
- A成型 = 1.143 的 **95% CI ≈ [0.96, 1.32]** —— **下界已低于阈值 1.0**
- 旁证：n=60 时 `ATTRITION=1.00` 的 A成型 恰好 = **1.000**，正压在阈值线上

**结论：T-A′ 离失败只有约 1.6~2.0 个标准误。**

> 🟡 **一处必要的自我更正（避免过度指控）**：我把 geo8 + attrition8 **完整重跑了第二遍**（见 §1.3 留档），两次输出**逐位相同**（A成型 1.143 / B全程 0.000 / B雪崩 0.000 / 起飞率 B 1.000、A 0.617）。因为所有脚本都用固定 seed（`PyRandom(20261002)` / `(20260930)`）且 GDScript 无并发不确定性，**这些套件是确定性的 —— 它们不会 flaky，CI 里今天跑和明天跑都是 1.143。**
> 所以这条发现**不是"测试会随机翻红"，而是"裕度太薄导致的脆弱性（fragility）"**：
> · **不会**因为随机性自己变红；
> · **会**因为 A 路径 shop AI / 构筑序列 / 怪物参数 / `WARMUP` 的任何一处微调，越过 1.0 这条线而变红 —— 而那次变红**未必代表机制真的失效**，只是均值掉到了阈值下。
> 换言之：这条判据**缺少区分"真回归"与"噪声位移"的能力**。这正是它必须被修成分布型判据的理由（见下 (ii)），而不是"它会 flaky 所以要隔离"。

**(ii) 统计量：用 300 局均值判定一个"单局可感知性"命题，是口径错配。**
"机制对高风险画像可感知"是 **per-run** 属性，判定式却用**跨 300 局的期望值**。二者不可互换：

- 探针单局实证：A 路径 W6–12 塔死 = **4**（集中在 W10/W11）；
- 300 局均值 = **1.143**。

两者相差 3.5 倍，说明分布**高度右偏**（大量 0 + 少数 4）。粗估约 **7 成的局在 W6–12 一次塔死都不会发生**（此比例建议补 per-run 直方图实测确认，我未改测试代码去采）。
也就是说：**均值 ≥1 无法区分"多数局都能感知到"与"少数局偶发尖峰"**，而后者的设计含义完全不同。

> **建议的修法（交文策渊/程基岩定夺，我只给测试口径建议）**：把 T-A′ 改写成分布型判据，例如
> `P(单局 A 成型期塔死 ≥1) ≥ 0.5` 或 `A 成型期塔死中位数 ≥1`，
> 或保留均值但把阈值下调并同步登记"均值 1.143 对应的 per-run 命中率"。无论选哪种，**必须先补一个 per-run 分布统计输出**，否则判据永远在黑箱里。

- ✅ **确认为存量问题**：未改动的 slice8 单独跑即可复现，与径向迁移无因果关系。技术附录 §"默认入口回归与已有遗留"的自述属实。
- 🔴 **但它污染 CI 信号**：只要这个泄漏在，"退出码 0 + stderr 非空"就会成为常态，真正的回归失败**混在一堆红色 ERROR 里没人看得见**。这与 R-1（无 CI）叠加后，等于**回归信号不可用**。
- **处置建议（P2，但不建议无限期拖）**：
  1. 短期：在 `run_tests.gd` 退出前显式 `free()` 所有 Node / 释放 CanvasItem（技术附录已指出方向：旧 UI 生命周期）；
  2. 中期：给回归入口加一条"**stderr 白名单**"机制——把已知的 TextServer/Font RID 泄漏登记为白名单，其余 ERROR 一律非零退出。这样泄漏还在，但不再掩盖真信号。
  3. **不建议**把它当成本次迁移的阻塞项（它不该由径向迁移买单）。

### 4.3 遗留②：工作区未纳管 —— **P2，风险低于初判**

实测分类（`git status --porcelain`，共 **217** 项）：

| 类别 | 数量 | 风险 |
|---|---|---|
| `design/phase2/numeric-sim/*` 导入产物（`.translation` / `.csv.import` / `.png.import`） | 139 | 🟢 低：纯派生物，但会让每次 `git status` 变脏、易误提交 |
| `*.gd.uid` | 63 | 🟡 见下 |
| `.workbuddy/memory/*.md` | 3 | 🟢 低：本地记忆，建议纳管或加忽略 |
| `docs/phase3/*.png` + 孤立 `.import` | 12 | 🟡 注意：存在 **`.import` 未纳管而其 `.png` 已纳管**的错配（如 `slice3-skeleton.png.import`） |

**关于 63 个 `.gd.uid`：我实测降级了它的风险。** Godot 4 的 `.gd.uid` 存放脚本的 `uid://` 常量，若被跨机器重新生成，引用它的资源会断链。我检查了工程内所有资源文件：

```
grep -c "uid://" scenes/*.tscn scenes/*.tres
  → scenes/battle_shop.tscn:0
  → scenes/main.tscn:0
```

**没有任何 `.tscn` / `.tres` 使用 `uid://` 引用**（全部走 `res://` 路径）。因此即使 `.gd.uid` 全部重新生成，**也不会产生断链**。

→ **风险从"P1 潜在断链"降级为 P2"导入抖动与提交噪声"**。

补充一个实测澄清：磁盘上 `.uid` 共 **63** 个，`git ls-files` 纳管 **0** 个 —— 即现状是**一致地"全部未纳管"**，并非"部分纳管/部分忽略"的混合态。混合态才是真正危险的（同一批文件在多机间 uid 漂移且无法复现），当前不属于这种情况。剩余影响只有两点：新克隆机器上 Godot 会重新导入并生成新 uid 文件 → 工作区永远脏；`git add .` 极易把 63 个文件误提交进去。

**处置建议**：
1. 在 `.gitignore` 补 `*.translation`、以及 `docs/**/*.import`（若不想纳管截图）；
2. 明确二选一并写进 README：要么 **全部纳管** `.gd.uid`（推荐，保证多机 uid 一致、消除导入抖动），要么 **全部忽略**（当前状态，可接受）——**关键是别滑向混合态**；
3. `docs/phase3/` 下存在 **`.import` 未纳管而其 `.png` 已纳管**的错配（如 `slice3-skeleton.png.import`），建议成对处理。
