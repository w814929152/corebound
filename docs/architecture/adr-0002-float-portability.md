## 1. 上下文

切片2 移植「战斗循环 + 商店/贪心 AI + 主循环 + 判据统计」时，决定性跑（rng=null）**全对**，
但 MC 300 局的 **B 起飞率是 89.3%，金标本是 91.3%**（差 2.0pp，正好压在主理人给的 ±2pp 容差线上）。
用户给的验收条件是「起飞率允许 ±2pp，但**起飞波次必须吻合**」——
而具体到局，B 第 18 局的起飞波是 **15 vs 金标本 13**，所以这不是"能接受"，必须查到根因。

二分定位链路（每一步都有实跑证据）：

1. MC 前 20 局逐局起飞波对照 → A 全对，B **第 18 局（下标 17）首个分歧**（15 vs 13）。
2. 逐波对照该局 → W1–W6 完全一致，**W4 的塔位分布先分叉**：
   Python `S3:Arrowh2 S5:Arrowh1` / GDScript `S3:Arrowh1 S5:Arrowh2`。
3. W4 商店逐动作日志 → **第 4 个动作**：候选 `up Arrow@3 / @4 / @5` 在 Python 里 ΔDPS
   **精确并列**（`9.406670173149649`），贪心 `max` 取第一个 → `@3`；
   GDScript 里 `up Arrow@5` 大了 **2.9e-14** → 取了 `@5`。
4. 一个塔位的差别被后续 16 波复利放大 → 起飞波 13 → 15。

→ **根因类型**：不是口径分歧（口径全程未动），而是 **1 ULP 级浮点噪声在"并列候选"上翻转选择**。
这类 bug 的决定性特征是：**决定性跑看不出来，只有 MC 能抓到**。

## 2. 三个末位分歧源（全部实测，不是推测）

### 2.1 `pow()`：整数指数幂差 1 ULP

```
Python 1.06 ** 6       = 1.4185191122560004
Godot  pow(1.06, 6.0)  = 1.4185191122560006     ← 差 1 ULP（2.2e-16）
真值 1.06^6            = 1418519112256 / 10^12 = 1.418519112256（有限小数，可精确判定谁对）
```

底数 1.000~1.120 × 指数 0~80 共 **2025 个采样点**：

| 比较对象 | 不一致数 |
| --- | --- |
| Godot `pow()` vs Python `**` | **1731 / 2025（85%）** |
| Python `**` vs `Fraction` 精确值后舍入 | **0 / 2025** → Python 侧**恒为正确舍入** |
| Godot `pow(h, 0.6)`（非整数指数，h=1..200）vs Python | **0 / 200** → 非整数指数本来一致 |

推测：Godot（MSVC 构建）的 `Math::pow` 与 CPython 走的 libm 实现/编译选项不同（`/fp:fast` 一类）。

### 2.2 `sum()`：Python 3.12+ 的 float 快路径是 Neumaier 补偿求和

`subtotal = sum(p["dps"] for p in per_tower)` 在 CPython 3.12+ **不是**朴素左结合累加：
`bltinmodule.c` 对 float 走 `f_result` / `f_result_err` 双累加器，最后返回 `f_result + f_result_err`。

关键差别：**补偿求和对同一多重集与次序无关**，朴素累加不是。
而贪心 AI 会给「升级 S3」和「升级 S5」各算一次 subtotal —— 二者逐塔 dps 是同一多重集、只换了位置。

实测（§1 的 W4 step2，四个并列候选）：

| 实现 | up@0 / @3 / @4 | up@5 |
| --- | --- | --- |
| Python（`sum()`，补偿） | 9.406670173149649 | 9.406670173149649 |
| GDScript（`+=`，朴素） | 9.406670173149**635** | 9.406670173149**649** |

### 2.3 浮点**字面量解析**：Godot 不是正确舍入（只影响测试金标本，不影响运行时）

```
Python float('186.26806084384762')  = 0x1.74893f455b53dp+7
Godot  字面量 186.26806084384762    = 0x1.74893f455b53cp+7   ← 低 1 ULP
Godot  字面量 186.268060843847620   = 0x1.74893f455b53dp+7   ← 加一位反而对了
Godot  字面量 3.07925140603429918e+03 ≠ 3079.251406034299    ← 换 18 位又错
```

**成败与位数不成单调关系**，改生成器的格式化串无法根除。
运行时只用 `1.42` / `0.045` / `1.03` / `0.6` 这类短字面量，实测全部解析正确，故**不影响引擎**。

## 3. 备选方案

### 方案 A（**已采用**）：在 GDScript 侧复刻 Python 的浮点语义

- 新增 `fp_pow.gd`：double-double（Dekker `two_prod` + `two_sum`）二进制快速幂，
  最后一次加法完成**单次舍入** → 正确舍入。整数指数走 `pow_int()`；非整数指数（如 `h ** 0.6`）仍用 `pow()`。
- 新增 `fp_sum.gd`：逐行移植 CPython 的 Neumaier 快路径 `sum_py()`，用于 `subtotal` / `aoe_total` / `aux_parts`。
- 逐波原始列的金标本比对用 `TOL_ROW = 1e-15`（≈4~5 ULP）而非逐位判等，并在测试里**打印实际最大偏差**。

- ✅ 与金标本**逐位**对齐：5528 个 `pow_int` 采样点 0 不一致；MC 前 20 局起飞波 A/B 全部逐位相同；
  B 起飞率 89.3% → 89.7%（只修 pow）→ **91.3%**（再修 sum）= 金标本值。
- ✅ 不改任何口径（`kr_mode` / `link_rule` / `hp_growth` … 全程未动）。
- ⚠️ 引入两个非惯常的 helper，需要在编码规范里点名，否则后续新代码会绕过它们。
- ⚠️ `pow_int` 有运行时成本（靠 `{底数: {指数: 值}}` 二级缓存压下去；MC 300 局 B 约 50 s）。

### 方案 B：放宽容差，把 2pp 当作"随机序列实现差异"接受

- ❌ **不做**。用户明确要求"起飞波次必须吻合"，而具体到局已经分叉（15 vs 13）；
  且实测证明差异**不是**随机序列造成的（A 路径全程不受影响，B 路径修完逐位相同），
  是确定性的浮点语义差异 —— 接受它等于把 bug 藏起来。

### 方案 C：改金标本 / 改判据

- ❌ **不做**。与 ADR-0001 的方案 C 同型：拿实现改文档/金标本，正是本项目要避开的坑。

### 方案 D：把金标本期望值改成"挑一个能被 Godot 正确解析的字面量写法"

- ❌ **不做**。§2.3 已证明存在能匹配的字面量（加一位即可），但那样做等于
  **让实现去反向塑造金标本**，与"不擅自凑数"的要求直接冲突。

## 4. 决定

**✅ 采用方案 A，主理人 2026-10-01 追认，N1/N2 提升为全工程强制编码规范。**

三条处置全部落地，全量自测 **2228 项断言 / 0 失败 / 退出码 0**：
定稿判据链 16 条逐条对上，MC A 69.3% / B **91.3%**，中位起飞波 A W8.0 / B W13.0，
MC 前 20 局逐局起飞波 A/B 逐位相同，决定性跑逐波原始列最大相对偏差 **1.712e-16**（验收线 1e-6）。

主理人拍板核验结论（本 ADR 证据链扎实，予以追认）：
1. **根因定位方法可信**：二分定位到「B 局第 18 局 W4 step2 的并列候选 ΔDPS」这一具体塔位分叉，
   因果链表格（89.3% → 89.7% → 91.3%）逐步收敛，不是"碰巧调通"。
2. **拒绝凑数是正确的**：工程主理人明确否决了方案 D（挑一个能被 Godot 正确解析的字面量写法），
   与 ADR-0001 方案 C 同型——拿实现反向污染金标本是本项目的红线，此处置守住了。
3. **不改任何口径**：`kr_mode`/`link_rule`/`ntower_mode`/`hp_growth` 等全程未动，
   这是"移植正确"而非"平衡重做"，符合切片定位。

**N1 / N2 现为全工程强制规范（进控制清单）**：

- **N1** —— 凡是**指数为整数**的幂（软 cap 的 `κ^lv` / `κ^cap` / `decay^(lv−cap)`、
  共鸣的 `(1+κ_r)^E`、血量的 `hp_growth^(w−1)`、`10^nd`），**必须**用 `FpPow.pow_int()`，
  禁止直接 `pow()`。非整数指数（塔层 `h ** 0.6`）走 `FpPow.pow_py()`。
- **N2** —— 凡是移植 Python 的 `sum()`（float 序列）**必须**用 `FpSum.sum_py()`，
  禁止 `+=` 朴素累加。整数序列（如 `sum(t.attach.values())`）不受影响，可照常累加。

## 5. 后果

- **正面**：GDScript 引擎从此与 Python 金标本在 MC 层面**逐位可复现**，
  后续任何"改一个 1ULP"的回归都会被 MC 前 20 局起飞波探针抓住（本次就是它抓到的）。
- **成本**：两个新文件 + 4 个呼叫点改造；`pow_int` 的 dd 快速幂在热路径上靠缓存兜底。
- **风险**：
  1. 若将来换平台/换 Godot 版本，`pow()` 的偏差方向可能变化 —— `fp_pow.gd` 只依赖 IEEE-754 双精度与
     Dekker 分裂常数，与 libm 无关，因此**只会更稳不会更差**。
  2. `TOL_ROW = 1e-15` 是权宜。若未来 Godot 修好字面量解析，测试 [0] 段的两条"参考输出"会翻成 `true`，
     届时应把 `TOL_ROW` 收紧回逐位判等（测试里已留注释）。
  3. 切片1 的 `tests/golden_reference.gd` 仍用 `%.17g`（17 位十进制），可能有同类解析噪声。
     切片1 在 1e-15 容差下全过，暂不改动；若要统一口径建议一并切到 `%.17e` 并重跑。
- **不改的东西**：任何口径参数（`kr_mode` / `link_rule` / `ntower_mode` / `hp_growth` /
  `hp_base` / `focus_per_layer` / `synergy_on` / `salvage_on` / `pity`）**一个都没动**。
