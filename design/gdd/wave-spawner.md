## 1. 系统目标（System Goal）

### 1.1 一句话

> `wave-spawner` 是这局的**时钟与压力源**。它必须把「玩家还有多少时间」和「玩家还差多少输出」这两件事，翻译成一条**可预测、可归因、可观赏**的怪物流：什么时候来、从哪条路来、长什么样、打到谁、漏了几只。

### 1.2 与支柱的兑现关系

| 支柱 | 本系统如何兑现 | 若不满足则 |
|---|---|---|
| **P1 不动如山 · 站位即策略** | 怪物的路径与塔位的距离是**固定的**（`d_path` 常量表）→ "这座塔会不会挨打"是**地图给的、玩家可读的事实**，不是随机数。站位从「覆盖 × 链接」二维升级为「**覆盖 × 链接 × 暴露**」三维 | 若怪物随机打塔 / 打谁由 RNG 决定 → 暴露度不可预判 → P1 塌一格 |
| **P2 雪崩无上限** | 雪崩期（W13+）`spawn_window = 1.00` → 怪物**全程均匀涌入**，屏幕被弹幕填满；同时 DPS ≫ 怪物 HP → **塔在 W13+ 几乎不再受创**，塔死亡机制自然退场（Submission 美学完整保留） | 若后期怪物仍集中在前段涌入 → 屏幕填不满；若后期怪仍能打到塔 → "观赏自己的造物"被破坏 |
| **P3 每局一个新解** | 怪物构成（Rush/Swarm/Tank）与**暴露格局**（哪些塔位贴路由地图决定）共同构成新的随机变量；T1 多地图后每局不同 | 若怪物构成恒定且地图恒定 → 少一个随机维度 |
| **P4 零操作 · 高密度** | 玩家对怪物**零输入**（不能集火、不能减速、不能拉怪）。波次压力只通过**安全窗的 build 决策**被回应 | 若引入"手动集火/手动加速"→ 直接违反 P1 与 Q6 |

### 1.3 本系统的三条设计红线（自检用）

| # | 红线 | 出处 |
|---|---|---|
| 🔴 **W-C1 · 守恒红线** | 任何新增的怪物分化（构成 / Elite / 速度）必须同时满足：**总 HP 守恒**（`Σ 只数 × 每只HP = N(w) × HP_unit(w)`）· **只数守恒**（`Σ 只数 = N(w)`）· **在场时间守恒**（`Σ p_i / m_spd_i = 1.00`，即加权平均在场时间 = `t_reach = 10.0s`）。**三条缺一即破坏既有校准** | 本文档 §2.5 · 定稿数值关已关闭 |
| 🔴 **W-C2 · 失败唯一性红线** | **核心 HP 归零是唯一的失败来源**。🔴 **禁止**新增任何"塔全灭 = 失败""漏怪数超限 = 失败""超时 = 失败"等判定 | 概念 §10 Q5 · `mechanics-tower-life-death` Q-T7 |
| 🔴 **W-C3 · 时间轴红线** | 怪物移动 / 攻击 / 刷怪计时**必须消费被 `Engine.time_scale` 缩放后的 `delta`**（商店打开 0.35× → 怪物同步变慢，这是设计意图；安全窗 `time_scale=0` → 完全静止）。🔴 **但不得用帧计数或墙钟**（会漏帧 / 减速失效）。几何类的**暴露度与路径采样是静态预计算**，不进帧循环 | 概念 §2.1 C1 · `core-defense` C-2 |

### 2.4 波次节奏与心流三阶段

#### 2.4.1 三个节奏参数（🔴 **F-7 首次登记** · sim 真身 `corebound_sim_v03.py:155-157`）

```
D(w)             = 28.0 + 2.2 × w                    # 波次刷怪总时长（秒）
t_reach          = 10.0                              # 单只怪物从出生到抵达核心的在场时间（秒）
spawn_window(w)  = 0.30  (w ≤ 5)                     # 苟活期：前 30% 窗口集中涌入（surge）
                 | 0.60  (6 ≤ w ≤ 12)                # 成型期：前 60% 窗口涌入
                 | 1.00  (w ≥ 13)                    # 雪崩期：全程均匀涌入

→ spawn_span(w)  = D(w) × spawn_window(w)            # 实际刷怪窗口长度
→ interval(w)    = spawn_span(w) / N(w)              # 逐只出生间隔
→ 战斗时长上限   = D(w) + t_reach                     # 最后一只出生 + 走完全程
→ 阈值 DPS       = HP_budget(w) / (D(w) + t_reach)   # 「本波刚好清完」所需的 DPS（sim 的 threshold）
```

> 🔴 **为什么这三个数必须登记而不能另起**：它们出现在 `threshold = total_hp / (D + t_reach)` 的**分母**里 —— 起飞判据（`DPS ≥ threshold`）由它们直接决定。**改 `wave_dur` = 改难度曲线 = 全量重扫**。本文档**只登记，不改**。
> 🟢 **与概念 §8.1 的一致性**：概念写「起飞判据 = `DPS(w)/总HP(w) ≥ 1.0`」，其可执行的真身即 sim 的 `DPS ≥ total_hp / (D + t_reach)`。两者是同一条判据的两种写法，**以 sim 为准**（它有单位、可算）。

#### 2.4.2 三阶段的压力特征（心流曲线的落地）

| 阶段 | 波次 | `spawn_window` | 怪物压力特征 | 核心 HP 预期 | 玩家动作重心 | 主导情感 |

### 2.5 怪物构成（🔴 W-C1 守恒红线 · 三原型分化）

> **问题**：概念 §5 定稿 MVP 有 **3 种怪物**（Rush 快速低血 / Tank 高血慢速 / Swarm 集群），但 sim 真身只有**一种**基准怪（`hp = 16 × 1.42^(w-1)`，`N = 8 + 1.6w`）。
> **解决**：把三种原型建模为**同一个 HP 预算的三种"重新分配"**，用三条守恒约束锁死 —— 这样"分化"与"校准"可以兼得。

#### 2.5.1 权威量（不可动）

```
HP_unit(w)     = 16 × 1.42^(w-1)                 # A15 · 单只"基准怪"HP
N(w)           = round(8 + 1.6 × w)              # 概念 §8.1 · 每波只数
HP_budget(w)   = N(w) × HP_unit(w)               # ★ 每波总 HP 预算 —— 真正的权威量
```

#### 2.5.2 🔴 W-C1 三条守恒约束（本文档新增内容必须全部满足）

| # | 约束 | 公式 | 为什么必须守恒 |
|---|---|---|---|
| **C-1** | **总 HP 守恒** | `Σ_i 只数_i × m_hp_i × HP_unit(w) = N(w) × HP_unit(w)` ⟺ **`Σ_i p_i × m_hp_i = 1.00`** | 总 HP 进 `threshold`，决定起飞点 → 一动即重扫 |
| **C-2** | **只数守恒** | `Σ_i 只数_i = N(w)`（`p_i` = 只数占比，`Σ p_i = 1`） | 漏怪伤害是 **50/只** → 只数变化 = 漏怪压力变化 → 一动即改难度 |
| **C-3** | **在场时间守恒** | `Σ_i p_i / m_spd_i = 1.00`（加权平均在场时间 = `t_reach = 10.0s`） | 在场时间 = 挨打时长 → 一动即改清场难度 |

#### 2.5.3 ✅ 定稿构成（唯一同时满足 C-1 / C-2 / C-3 的整洁解）

| 原型 | 只数占比 `p` | **HP 乘数 `m_hp`** | **速度乘数 `m_spd`** | 速度 (u/s) | 在场时间 (s) | 单只 HP（`×HP_unit`） | 设计角色 |
|---|---|---|---|---|---|---|---|
| **Rush** 快速低血 | **40%** | **0.60** | **4/3 ≈ 1.333** | 13.47 | **7.5** | 0.60× | 抢线压力 · 制造"来不及" |
| **Swarm** 集群 | **40%** | **0.40** | **1.000** | 10.10 | **10.0** | 0.40× | 弹幕填充 · P2 视觉载体 |
| **Tank** 高血慢速 | **20%** | **3.00** | **2/3 ≈ 0.667** | 6.73 | **15.0** | 3.00× | **漏怪主因** · 单体怕硬 |

**三条守恒验算（逐位）**：
- C-1：`0.40×0.60 + 0.40×0.40 + 0.20×3.00 = 0.24 + 0.16 + 0.60 = ` **`1.000` ✓**
- C-2：`0.40 + 0.40 + 0.20 = ` **`1.000` ✓**
- C-3：`0.40/1.3333 + 0.40/1.000 + 0.20/0.6667 = 0.300 + 0.400 + 0.300 = ` **`1.000` ✓**（等价加权在场时间 `0.4×7.5 + 0.4×10.0 + 0.2×15.0 = 3.0+4.0+3.0 = 10.0s ✓`）

> 🎯 **为什么这组数字是"整洁解"**：Rush/Tank 的速度取 `4/3` 与 `2/3`（互为对称的 ±1/3），Swarm 取 `1.000`（= sim 基准）；HP 取 `0.60 / 0.40 / 3.00`。**三条守恒全部精确落在 1.000，无浮点凑数**。
> 🟢 **Tank 是设计的核心**：20% 的只数吃掉 **60% 的 HP 预算**，且在场 15s（最长）。→ **Tank 是唯一的"能活着走到核心"的怪** → 漏怪归因于「我没能处理 Tank」而不是「我运气不好」（概念 §4.1 胜任感）。这与概念 §8.1「吃不到 `AllIn ×1.6` → 依然怕硬（Tank / Elite / Boss 单体）」完全同向。

#### 2.5.4 Elite 波（概念 §5「每 5 波 1 个 Elite」· HP 守恒浓缩口径）

> 🔴 **一处跨文档冲突的消解**：`mechanics-tower-life-death` §3 玩法⑤ 说「MVP 怪物只有 3 种，**不新增**」，而概念 §5 说「每 5 波 1 个 Elite」在 MVP 内。
> ✅ **本文档的裁定**：**MVP 的 Elite = 词缀（affix），不是新原型** —— 它是"某几只普通怪被放大 + 加视觉标记"，**AI 完全不变**；**Sapper（破塔者）= 会改 AI 的 Elite 词缀**（🟢 **v0.5：已随 Elite 进实机**，见 §2.11）。两边都满足。

```
Elite 波 = {5, 10, 15, 20, ...}（每 5 波）
n_e(w)        = max(2, round(0.10 × N(w)))         # Elite 只数（W5:2 / W10:2 / W15:3 / W20:4）
m_hp_elite    = 2.5                                 # Elite HP 乘数（浓缩）
c(w)          = (N − 2.5·n_e) / (N − n_e)           # ★ 普通怪 HP 乘数的守恒缩放系数
                → W5 0.786 / W10 0.864 / W15 0.845 / W20 0.833
```

> 🔴 **守恒保证**：Elite **不加总 HP、不加只数**，只是把该波 HP 预算的 25% 浓缩到 10% 的只数上，其余 90% 的只数按 `c(w)` 等比例下调 → `总 HP` 与 `只数` 双双不变（C-1 / C-2 均成立）。速度沿用宿主原型（C-3 自动成立）。
> 🎯 **设计意图**：Elite 波是**节奏标点**，不是难度台阶 —— 它制造「忽然来了几只大的」的**可读性事件**，让玩家在波次间有话可说（"W10 那两只大 Tank 我差点没打掉"），而不改变任何曲线。

### 2.6 ★ 怪物仇恨 AI 状态机（Q-T3 机会型仇恨 · 🔒 实现进 T1）

#### 2.6.1 状态机

```
                        ┌─────────────────────────────────────────┐
                        │                                         │
   [Spawn] ──→ [Marching] ────────────────────────────────────────┤
                  │  沿路径前进：s += v₀ × m_spd × dt              │

                  │  每 AGGRO_TICK (0.1s) 判定一次：                │
                  │  C = { 塔 i │ ¬disabled_i ∧ dist(self, slot_i) ≤ AGGRO_R }
                  │  C ≠ ∅ ?                                      │
                  │         ├─ 否 → 继续 Marching                  │
                  │         └─ 是 → target = argmin dist → ↓       │
                  ↓                                               │

#### 2.6.4 🟢 为什么"吸怪钉子"不会成为主导策略（本文档的诚实论证）

> **风险**：既然怪物会停下打塔，玩家能不能把一座**深塔放在 S0**（暴露弧长 21.67，最长）当"钉子"，让怪物永远停在它前面 → **零漏怪 → 必胜**？

**不会，三条机制保障**：
1. **伤害叠加（R10）**：塔的 HP 是 `HP0 × h^0.6`（次线性），而攻击它的怪物数是**线性叠加**的。W20 有 8 只 Tank 同时围上来 → 塔必死。`h=133` 的深塔也只比 `h=1` 硬 18.8 倍，扛不住 40 只怪的集火。
2. **暴露弧长只有 52.6%**：塔只能吸住**正在它危险段内**的怪；S4/S5 段（占 47.4%）的怪直冲核心 → **必然有漏怪压力**。
3. **塔死了就不吸了**：`Disabled` 塔被排除出候选集（R5）→ 怪物立刻恢复前进 → 钉子失效时间 = 塔的存活时间。

> ✅ **结论**：吸怪是**正当的战术收益**（肉盾玩法② 的地基），不是漏洞 —— 它的代价是"塔会死 + 死塔期间零输出"。这让"贴路位"从"纯负收益"变成"**高覆盖 + 高风险 + 可作为肉盾**"的立体选择，正是 P1 想要的。

### 2.7 ★ 伤害分配口径（🔴 **F-5 首次登记** · MVP 权威口径）

> 🔴 **这是一个此前没有任何 GDD 写过、但直接决定"实现能否与模拟对上"的口径。** sim 真身 `simulate_wave` 的实际做法是：
> ```
> dmg = Delivered × dt                       # 全场 DPS 池，逐塔求和后的总量
> monsters.sort(key=lambda m: m[1])          # ★ 按"剩余在场时间 t_reach"升序 = 最接近核心的排最前
> for m in monsters:                          # 逐只填满；一只被打死后，溢出伤害结转给下一只
> ```

| # | 规则 | 口径 |
|---|---|---|
| **W-A1** | **分配粒度** | **聚合池**：`Delivered`（`damage-pipeline` 阶段 C 的全局输出）作为一个总量，不区分是哪座塔打的 |
| **W-A2** | **目标排序** | **`first` 集火**：按「距核心最近」优先（= 剩余在场时间最小者） |
| **W-A3** | **溢出处理** | **结转**：一只死亡后剩余伤害**继续打下一只**，不浪费 |
| **W-A4** | **有效射程** | **不判定**：聚合口径下怪物"在哪被打"不由几何决定（射程效果已由 `CoverageScore` 聚合常量 A 0.78 / B 0.95 表达） |

> 🟡 **观察项 O-1（交程基岩，T1 评估）**：逐塔就近分配在**视觉上更正确**（怪物应该在有塔覆盖的段落才掉血）。若 T1 要切，**必须与逐塔几何 `CoverageScore` 的整体重标定（`core-defense` §8 交接点 2）绑定一起做**，单独切会两头不讨好。**MVP 不动。**

### 2.10 怪物对塔的伤害口径（🔒 T1 · 与 V-1 扫参的关系 · 🔴 **F-4**）

#### 2.10.1 模型形式（本文档给形式，标量交 V-1）

```
dmg_to_tower(m) = ATTRITION × HP0 × m_dps(prototype) × dt

  ATTRITION  = 唯一待扫复合参数（mechanics-tower-life-death §4.2 V-1）
  HP0        = 120（Q-T2 定稿）
  m_dps      = 原型对塔伤害系数（见下）
  dt         = 波次时钟步长（受 time_scale）
```

| 原型 | **`m_dps`** | 说明 |
|---|---|---|
| Rush | **0.80** | 快但轻 |
| Swarm | **0.60** | 最轻（集群靠数量） |
| **Tank** | **2.20** | 🟢 **塔的杀手** —— 与它"漏怪主因"的角色一致 |
| 验算 | `0.40×0.80 + 0.40×0.60 + 0.20×2.20 = 0.32 + 0.24 + 0.44 = ` **`1.000` ✓** | 与 `m_hp` / `m_spd` 同族，归一化到基准怪 = 1.00 |

#### 2.10.2 ★ 一个关键发现：`HP0` 在"击毁时间"里被约掉

```
塔 HP_i      = HP0 × h^0.6                       （Q-T2 定稿）
击毁所需时间  = HP_i / (ATTRITION × HP0 × m_dps)
             = (h^0.6) / (ATTRITION × m_dps)     ← ★ HP0 被完全约掉
```

> 🎯 **这正是 `ATTRITION` 能作为"唯一复合参数"被扫的数学原因**（`mechanics-tower-life-death` §2.1 已指出二者共轭，本文档给出显式形式）。→ **V-1 扫 `ATTRITION` 时，`HP0` 取 120 还是 240 对结果毫无影响**；真正决定游戏感的是下面这张换算表。

## 4. 交互流程（Interaction Flow）

### 4.1 一波的完整生命周期

```
[安全窗 / Idle] 玩家点「开始 Wave N」
   ├─ WaveDirector.w = N；state = Spawning；t_wave = 0
   ├─ 计算本波参数：N(w) / HP_unit(w) / D(w) / spawn_span / interval / 构成 / 是否 Elite 波
   └─ time_scale 恢复 1.0

[Spawning]（持续 spawn_span(w) 秒）
   ├─ 每 interval 秒生成 1 只（按构成比例轮转原型）
   ├─ 同时：怪物移动 / 塔开火 / damage-pipeline 输出 Delivered
   └─ 玩家可随时打开商店（time_scale → 0.35×，消耗 DilationBudget 20s/波）

[Fighting]（怪物行进与清剿）
   ├─ 每帧：s += v₀ × m_spd × dt
   ├─ 每 AGGRO_TICK：仇恨判定（🔒 T1 生效）
   ├─ 每帧：Delivered × dt 按 W-A1~W-A4 分配给怪物
   └─ s ≥ 101 → 漏怪 → Core.hp -= 50

[结算] 全部怪物已结算 或 t_wave ≥ D(w) + t_reach
   ├─ 残留怪物直接移除（不扣血、不给分）
   ├─ state = SafeWindow；time_scale = 0
   └─ 打开安全窗 UI（弃卡 / 卸下 / 拆塔 / 转型）

[SafeWindow] 玩家点「开始 Wave N+1」→ 回到顶部
```

### 4.2 怪物受击与死亡

```
[受击] Delivered 分配 → monster.hp -= dmg
   ├─ hp > 0   → 继续
   └─ hp <= 0  → kills += 1；Scrap += 2 + 0.5w（→ shop-reroll）；移除
```

> 🔴 **击杀收益 `scrap_per_kill = 2 + 0.5w` 是本系统转发给 `shop-reroll` 的**，本系统**不改**它（概念 §8.1 · `card-system` §1.4）。

### 4.3 塔受击（🔒 T1）

```
[AggroTower] 每帧：tower.hp -= ATTRITION × HP0 × m_dps × dt
   ├─ hp > 0   → 继续（塔体损伤演出 + 余光告警，T-C2）
   └─ hp <= 0  → tower.disabled = true
                 ├─ Raw_i 末尾 × 0（结构性因子，不进 7 乘区）
                 ├─ 🔴 不重建 LinkGraph / 不重算 E_i（断输出不断链，Q-T5）
                 ├─ 该塔退出所有怪物的候选集（R5）→ 怪物回 Marching
                 └─ 安全窗弹「处置提示」（修复 / 拆除 / 放着）◆合并列表（E-T2）
```
