## 0. 结论前置（给赶时间的人）

1. **管线分三阶段**：**阶段 A 前置派生**（塔位 / 建塔 / 拆塔 / 改装配时重算）→ **阶段 B 逐塔 `Raw_i`** → **阶段 C 全局聚合 `Delivered`**。全程**事件驱动**（dirty flag），**不是每帧算**。
2. **7 个数值乘区定稿顺序**：逐塔 `Stack → Resonance → Focus → AllIn`；全局 `Crossfire → Aux → Empowerment`。另有 **3 个结构性系数**不属乘区但必须先算：`Base(h^0.6)`（逐塔基数）、`CoverageScore`（逐塔覆盖）、`AoE 密度效率`（全局，位于 C 段首位）。
3. 🔴 **`Syn` 一次性 ×1.5 乘区删除**。Tag 不再直接乘 DPS，只通过 `TagTier → κ_tag / κ_r / StackCap` 三条路径间接起作用（概念 §2.4.7 早已如此，是引擎没跟上）。摘除是**口径修正，不是重标定**：`hp_growth=1.42` / `hp_base=16` / `focus=0.06` / κ / κ_r **一个都不改**。
4. **诚实说明「锁顺序」的真实目的**：都是纯乘法，**顺序不影响数学结果**。锁顺序是为了 ① **依赖正确性**（`Resonance` 必须在 `E_i` 之后、`Focus` 必须在 `L_i` 之后）；② **浮点确定性**（同一套乘法次序 = 同一串舍入，模拟与实现逐位可比）；③ **未来可维护性**（T1 若插入新乘区，有唯一合法插入点）。
5. **4 个必须写进实现手册的陷阱**（§2.6 / §4.2 / §5.4）：① `Resonance` 是**邻居**乘区，塔**自己不吃自己的层数**（`j ≠ i`），且**双向门槛 `h ≥ 3`**；② 缓存失效粒度——`Coverage/LinkGraph` 只在塔位变动重算，`E_i` 在**链接图变动 或 任一邻居 `h` 变动**时重算（买建筑卡是连锁 **5 连**重算，最易漏；射程已确认固定 → 原"六连"降为"五连"）；③ `Stack` 软 cap **必须在乘区内部夹取**（`softcap_pow` 分段），**禁止外部 `min(n, cap)`**；④ 🆕 **`LinkGraph` 不是地图静态常量** —— 邻接随**原型**变（射程 18/20/22 → 阈值 23.4/26.0/28.6），建/拆塔换原型就会改变邻接，**单测必须 pin 原型**。
6. **值域**：终局 `Delivered` 实测 **单核 A ≈ 1.09e7 / 多塔 B ≈ 5.0e6**（W20），理论上限 ~1e20 → **全程 double**，禁用 float32 分量；UI 走 **log10 缩写**；存档 / 种子**只存层数不存伤害**。
7. 🔴 **`Stack` 的多卡聚合 =「分组口径」**（§5.4，红线 **R-4**）：**复利组内部并联相加**（`1 + Σ(m_c − 1)`，= 引擎现行写法 = 定稿数值的扫描基础），**复利 / 加法 / 饱和三组之间串联相乘**（= `card-system` §5.6 字面口径）。全并联会让加法/饱和卡在终局沦为废卡（违反 C-1）；全串联会让同塔两张复利卡叠出**双指数**（`13,783×` vs `234×`，违反 P2/P3）。**MVP 每塔 1 张复利卡 → 三种口径逐位等价，零重标定。**

## 1. 系统目标（System Goal）

### 1.1 一句话

> 伤害管线是**全游戏数值正确性的中枢**：它把一个玩家的 build（塔位 + 层数 + 装配）唯一地映射成一个 DPS 数字，**不允许任何第二处代码再算一遍**。

### 1.2 与支柱的兑现关系

| 支柱            | 本系统如何兑现                                                                                | 若不满足则                           |
| ------------- | -------------------------------------------------------------------------------------- | ------------------------------- |
| **P1 不动如山**   | 管线只吃**静态状态**（塔位 / 层数 / 装配 / 链接），不含任何玩家输入的运行时项 → 零微操                                    | 若伤害依赖"集火 / 释放时机" → 违反 P1        |
| **P2 雪崩无上限**  | `Stack`（深度）× `Resonance`（广度）两条**指数**出口都在本管线内，且**软 cap 保证衰减不归零**（R12）                   | 若用硬 cap 或加法 → 起飞数学不成立（v0.3 已实证） |
| **P3 每局一个新解** | 两条主干的**主导乘区不同**（单核 = `Stack` ×10142；多塔 = `Resonance` ×37.76，v0.4 §1.1）→ 每局的主导项由发牌与拓扑决定 | 若所有 build 的主导乘区相同 → 主导策略        |
| **P4 决策而非动作** | 管线的每一次重算都由**玩家的不可逆决策**触发（买 / 放 / 拆 / 卸），且重算结果立刻可见 → 决策有即时反馈                            | 若重算延迟一帧以上或需玩家手动刷新 → 反馈链断裂       |

## 2. 核心机制（Core Mechanics）

### 2.1 为什么必须有这一份 GDD（问题陈述）

概念 §11.3 的原话：**「`damage-pipeline` 的乘区顺序是本作最易出错的一处」**。原因有三：

1. **乘区多且分属两个作用域**：逐塔 4 个 + 全局 3 个 + 3 个结构性系数，共 10 个量相乘；
2. **乘区之间有依赖，不是平铺**：`Resonance` 依赖 `LinkGraph` 与 `h_j`；`Stack` 依赖 `κ` 与 `StackCap`；`AllIn` 依赖 `CoreTower`；`Aux` 依赖挂件塔层数；
3. **纸面模拟与真实引擎必须逐位可比**：`corebound_sim_v04/v06` 的 300 局蒙特卡洛结论（起飞率 A 69.3% / B 99.0%）只有在**实现与模拟同一条乘法链**时才成立。

→ 因此本 GDD 的输出物是**一条可执行、可回归的结算链**，不是一组公式的罗列。

### 2.2 三阶段管线总览

```

> 📌 **Focus 预热门槛**（D-1 定稿，`focus_full=False`）：B5 按 `1 + 0.06 × L_i · min(1, h_i/8)` 计 —— **主塔层数 `h_i` 达 8 才全额**（`focus_min_h = 8`；未达 8 时线性爬升）。两条定稿路径终局 `h_i ≥ 8` → `ramp = 1` → **金标本逐位不受影响**。

> `Resonance` 虽然由邻居驱动，但它**逐塔取值不同**（`E_i` 是塔 i 的私有和）→ 归逐塔段。`Crossfire` / `Aux` / `AoE` 全场一个值 → 归全局段。

```
逐塔：Base → Stack → Resonance → Focus → AllIn → Coverage

> **为什么明知"顺序不影响乘积"还要锁（诚实说明）**：  
> ① **依赖正确性** —— `Resonance` 必须在 `E_i`（阶段 A）之后、`Focus` 必须在 `L_i` 之后、`AllIn` 必须在 `CoreTower` 之后。锁顺序 = 锁依赖。  
> ② **浮点确定性** —— 同一串乘法次序 = 同一串舍入。`1.09e7` 量级下不同次序会产生 `1e-9` 级相对误差，跨版本累积后会让"起飞波次"这种**阶跃判据**在边界抖动。  
> ③ **可维护性** —— T1 插入新乘区（如 `Empowerment`）时有唯一的合法插入点。

### 2.5 κ / κ_r / StackCap：Tag 的唯一出口（三条路径）

```

```


| 该 Tag 投入层数 `L_tag`                  | `κ_tag`（基准）                | `κ_r`              | `StackCap` |
| ----------------------------------- | -------------------------- | ------------------ | ---------- |
| 0–2 层（未协同）                          | `0.06`                     | `0.040`            | 50         |

### 2.6 🔴 四个必须写进实现手册的陷阱

#### 陷阱 1 · `Resonance` 是「邻居」乘区 —— 塔自己不吃自己的层数，且门槛是双向的

```
E_i = Σ_{j ∈ N(i)} (1 + h_j)        其中 j ≠ i   ← 塔 i 自己不进自己的和
      且要求 h_i ≥ 3 且 h_j ≥ 3                   ← 双向门槛（缺一不可）
```

| 场景                                       | 正确结果                                         | 常见错误                        |
| ---------------------------------------- | -------------------------------------------- | --------------------------- |
| 场上只有 1 座塔（无论 `h` 多大）                     | `E = 0` → `Resonance = ×1.00`                | ❌ 把 `h_i` 算进 `E_i` → 孤塔也吃复利 |
| `h_i = 1` 的占位塔，邻居是 `h=133` 的塔            | `E_i = 0`（自己没长成）→ `×1.00`                    | ❌ 只看邻居门槛 → 占位塔白嫖 ×1e2       |
| `h_i = 8` 的塔，邻居都是 `h=1` 占位塔              | `E_i = 0`（邻居没长成）→ `×1.00`                    | ❌ 忽略邻居门槛 → 白嫖               |
| 定稿多塔 B：`Arrow(h=133)` 与 `Cannon(h=8)` 互链 | `E_Cannon = 1+133 = 134`；`E_Arrow = 1+8 = 9` | —                           |

> **双向门槛是设计意图，不是实现巧合**：v0.3 §1.7 立 `link_min_level` 的 diegetic 理由就是「**塔要「长成」才会与邻居共振**」——没长成的塔既不发出也不接收。v0.4 定稿多塔 B 的逐塔明细（4 座 `h=1` 塔 `E=0`）证实标定用的就是双向口径。  
> 🔴 **因此 `card-system` §5.3 的文字公式 `E_i = Σ_{j 与 i 链接, h_j ≥ 3} (1+h_j)` 漏了 `h_i ≥ 3`** —— 已列入 §9 D-6 需回写。

#### 陷阱 2 · 缓存失效粒度：买一张建筑卡 = 5 连重算（最易漏）

> 🆕 **v1.0.2 修订**：`core-defense` CD-4 已确认 **MVP 射程固定，不随 `h` 变化** → 原第 6 环「`Coverage` + `LinkGraph` 重算」**在 MVP 不触发**，链路由「六连」降为「**五连**」。🔴 **这是"少做"不是"少漏"** —— 请不要为了保险在升级时无条件重算链接图（6 塔下每次升级多跑一次 union 覆盖 + 邻接重算，是白付的成本）；**但要把它写成一行显式注释**，否则 T1 一旦让射程随级变化，这里会静默漏掉。

详见 §4.2 完整矩阵。这里只点出**最容易漏的三条**：

| 漏了会怎样                             | 正确做法                                                                                                                                                                                                                                                                           |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 买建筑卡 → `h_j + 1` → **只重算了塔 j 自己** | 必须同时重算 **① `Base_j`** + **② 所有邻居的 `E_i`**（`j` 是别人的邻居）+ **③ `L_tag`**（Tag 投入层数 +1 → 可能跨档 → **全场 κ / κ_r / StackCap 重算**）+ **④ `AoE`**（有 Tag 塔层数之和变）+ **⑤ `CoreTower`**（`argmax L_i` 可能易主）。<br>❌ **`Coverage` / `LinkGraph` 不触发**（射程固定，CD-4） |
| ~~升级塔 → 射程变化 → 忘了重算链接~~               | ✅ **MVP 已无此风险**（射程固定）。⚠️ 但 `card-system` §4.4 交接点 1 / E6 仍按"射程随等级变"写 → 需回写（§9 **D-10**）。🔴 **保留一条保底断言**：单元测试里断言「升级塔后 `LinkGraph` 不变」，若 T1 改了射程规则，这条测试会先炸                                                                                                     |

#### 陷阱 4 · 🆕 `LinkGraph` 不是地图静态常量 —— 邻接随原型变

🔴 **链接判据是 `dist(i,j) ≤ 0.65 × (R_i + R_j)`，而 `R` 是原型属性**（`core-defense` CD-3：Arrow 22 / Cannon 18 / Frost 20 / Beacon 20）。因此**同一对塔位的链接阈值随两边原型变化**：

| 原型组合 | `0.65 × (R_i + R_j)` |
|---|---|
| Cannon–Cannon | `0.65 × 36 = 23.4` |
| Frost/Beacon–Frost/Beacon | `0.65 × 40 = 26.0` |
| Arrow–Arrow | `0.65 × 44 = 28.6` |

→ **链接图不是"地图加载时算一次的常量表"**，建塔 / 拆塔换掉原型就会改变邻接。🔴 **两个工程后果**：① 邻接表必须在**塔位或原型变动**时重算（这正是 §4.2 把 `LinkGraph` 挂在"建/拆塔"而非"初始化"的原因）；② **单测必须 pin 原型组合** —— 只 pin 坐标是不够的（方案 B 实测：全 Cannon 度 `[3,3,3,3,2,2]` avg 2.67，全 Frost/Beacon 度 `[5,5,5,5,4,4]` avg 4.67，混编 avg 4.00 —— **同一张地图，邻接差一倍**）。

#### 陷阱 3 · `Stack` 软 cap 必须在乘区内部夹取

```python
def softcap_pow(n, kappa, cap, decay):        # ✅ 正确：分段，衰减不归零
    if n <= cap:  return kappa ** n
    return (kappa ** cap) * (decay ** (n - cap))

# ❌ 错误写法 1：外部硬夹
n_eff = min(n, cap);  mult = kappa ** n_eff   # 第 cap+1 层起收益 = 0 → 硬墙，反 P2（R12）

# ❌ 错误写法 2：整体衰减
mult = kappa ** min(n, cap) * (decay ** max(0, n - cap)) if n > cap else kappa ** n
                                              # 等价于正确式（OK），但注意是 (kappa**cap) 不是 (kappa**n)
```

| 层数  | `κ=1.10, cap=100, decay=1.03` | 说明                   |
| --- | ----------------------------- | -------------------- |
| 100 | `1.10^100 = 13,780.6`         | 与定稿 `Stack_max` 逐位一致 |
| 101 | `1.10^100 × 1.03 = 14,194.0`  | **仍在涨**（+3%），不是归零    |
| 150 | `1.10^100 × 1.03^50 = 60,417` | 衰减但仍指数级增长            |

## 4. 交互流程（Interaction Flow）— 管线

### 4.1 结算主流程（参考实现，GDScript 伪码）

```gdscript
# 事件驱动：任何会改状态的玩家操作都调用 mark_dirty()，重算在**帧末**统一做一次。
# 塔数 ≤ 6，全量重算 < 0.1ms。🔴 MVP 禁止做增量优化（见 §5.6）。

func recompute(run: Run) -> void:
	if not run.dirty: return
	var ts := run.towers
	var n := ts.size()
	if n == 0:
		run.cache = DamageCache.empty()      # E1：Delivered = 0
		run.dirty = false
		return

	# ---------- A 段 ----------
	var h: Array[int] = []; var L: Array[int] = []
	for t in ts:
		h.append(t.h)
		L.append(sum(t.attached.values()))
	var Ltot := sum(L)

	var tag_invest := {}                                   # A6
	for i in n:
		var tg := ts[i].proto.tag
		if tg != null: tag_invest[tg] = tag_invest.get(tg, 0) + h[i]
		for card_id in ts[i].attached:
			var ct := CardDB[card_id].tag
			if ct != null: tag_invest[ct] = tag_invest.get(ct, 0) + ts[i].attached[card_id]
	# ⚪ 全局效果卡不计入 tag_invest（见 §9 D-7）

	var disc := 0.01 * clamp(run.n_tower_histmax - 2, 0, 4)  # A8 广度折价 ★读历史最大塔数(兜底①), 非当前 n
	var adj  := core_defense.link_graph(run)               # A5 ★依赖 core-defense
	var cov  := core_defense.coverage(run)                 # A4 ★依赖 core-defense

	var core := -1                                         # A11
	if Ltot > 0:
		core = argmax_stable(L)                            # 平局取「先达到该层数」者（E7）

	# ---------- B 段 ----------
	var per := []
	for i in n:
		var t := ts[i]
		var tag := t.proto.tag
		var inv := tag_invest.get(tag, 0) if tag != null else 0
		var k      : float = maxf(0.02, tier(inv, KTAG_TIERS) - disc)          # A8
		var kr     : float = tier(inv, KR_TIERS) if tag != null else 0.045     # A9 ★中性塔恒 0.045
		var scap   : int   = stack_cap_of(inv)                                 # A7（见 §5.4）

		var E := 0.0                                                           # A10
		if h[i] >= LINK_MIN_LEVEL:                                             # ★自己先要长成
			for j in adj[i]:
				if j != i and h[j] >= LINK_MIN_LEVEL:                          # ★邻居也要长成
					E += 1.0 + h[j]

		var base := t.proto.base_dps * pow(float(h[i]), 0.6)                   # B1
		var stack := 1.0                                                       # B2
		for card_id in t.attached:
			if CardDB[card_id].tag != tag: continue                            # ★Tag 过滤（见 §9 D-8）
			stack *= softcap_pow(t.attached[card_id], 1.0 + k, scap, 1.03)     # ★内置软 cap
		var res   := pow(1.0 + kr, E)                                          # B4
		var foc   := 1.0 + 0.06 * L[i] * min(1.0, h[i] / 8.0)                  # B5 ★预热门槛
		var ali   := 1.6 if (i == core and L[i] >= 0.60 * Ltot) else 1.0       # B6
		var raw   := base * stack * res * foc * ali * cov[i]                   # ★乘法次序锁死
		per.append({...})

	# ---------- C 段 ----------
	var subtotal := sum(per.map(func(p): return p.raw))
	var aoe_total := 0
	for i in n:
		if ts[i].proto.tag != null: aoe_total += h[i]                          # C1 只统计有 Tag 的塔
	var aoe := minf(AOE_CAP, 1.0 + AOE_PER * float(aoe_total))
	var cf  := 1.5 if n >= 3 else (1.25 if n == 2 else 1.0)                    # C2
	var aux := compute_aux(run)                                                # C3（§5.5）
	var emp := 1.0                                                             # C4（MVP 恒 1.0）

	run.cache.delivered = subtotal * aoe * cf * aux * emp
	run.dirty = false
	emit_signal("damage_cache_changed", run.cache)                             # UI 统一订阅
```

### 4.3 时钟分层（🟡 架构确认点 K —— `time_scale` 隔离）

本作有战术减速（`0.35×` / 新手 `0.25×` / 波次间暂停），因此**必须区分三套时钟**：

| 时钟                 | 受 `Engine.time_scale` 影响 | 用途                                                   | 实现建议                                                  |
| ------------------ | ------------------------ | ---------------------------------------------------- | ----------------------------------------------------- |
| **游戏时钟**（scaled）   | ✅ 是                      | 攻击间隔、弹道飞行、怪物移动、波次推进、DoT                              | `delta`（`_process` / `_physics_process`）              |
| **实时时钟**（unscaled） | ❌ 否                      | **减速预算 `20s/波`**、刷新成本递增周期、**伤害数字合并窗口 `100ms`**、UI 动画 | `Time.get_ticks_msec()` / `delta / Engine.time_scale` |
| **事件时钟**（无时钟）      | —                        | **管线重算、链接图、`κ` 全场重算**                                | dirty flag，**帧末统一结算一次**                               |

> 🔴 **交接点 K（架构层）**：**链接图与伤害管线重算必须走事件驱动路径，禁止挂在 `Timer` 或 `_process` 的计时器上** —— 否则减速时重算频率会跟着变慢，出现"减速期间数字不更新"的诡异 bug。  
> 同理，**伤害数字合并窗口必须用 unscaled 的 100ms**：否则 `0.35×` 减速下聚合窗口会变成实时 286ms，数字冒出来的节奏随减速变化 → 破坏可读性。

### 5.3 κ 判定口径（card-verify §3.4 + card-system §5.2）

```
κ_i = κ_tag(L_tag of 塔 i 的 Tag) − 0.01 × clamp(N_tower_histmax − 2, 0, 4)      下限 0.02
      🔴 N_tower_histmax = 本局历史最大塔数（只增不减, 兜底①）, 非当前场上塔数 N_tower
```

| `N_tower_histmax`（本局历史最大塔数） | ≤2       | 3    | 4    | 5    | ≥6       |
| ------------------------- | -------- | ---- | ---- | ---- | -------- |
| 广度折价                      | 0        | 0.01 | 0.02 | 0.03 | 0.04     |
| **κ（协同成立档 `κ_tag=0.10`）** | **0.10** | 0.09 | 0.08 | 0.07 | **0.06** |

> 🔴 **兜底①口径（card-system v1.1.5 定稿, 本表权威来源）**：折价项读 `N_tower_histmax`（**只增不减**）—— 铺满 6 塔后拆到 2 塔, 折价仍锁在 `0.04`（κ=0.06）不回升。🔴 **但档位项不受此保护**：拆塔销毁装配层会使 `L_tag` 下降 → `κ_tag` 档位仍可能从 0.10 掉到 0.06（`StackCap` 亦可能 100→50）。**工程不得把"折价不回退"过度实现成"κ 完全不变"**（详见 `tower-build` §2.5）。
> 🔴 **与 `Crossfire` 分属两个量**：`Crossfire`（C2）读**当前** `N_tower`（拆塔后降档 1.5→1.25）；κ 折价读 `N_tower_histmax`。见 §8.2b TB-5 拆分口径。

**两条必须写进实现的口径**

1. 🔴 **κ 是「逐塔当前值」，不是「逐层历史值」**：一座塔的**全部**强化层共用**当前** κ。建塔 / 拆塔 / 塔数变化 → **全场立即重算** → 深叠后期新建塔会**回溯下调**已有层数的利率。（定稿行为，非 bug；UI 需披露，见 card-system E11 / R-C1）
2. 🔴 **κ 判定与 `Focus` / `AllIn` 完全解耦**：后两者只吃「单塔效果卡层数」，不随 κ 变化。

**κ_r 取档口径**：取**该塔自身所属 Tag**的档位（`own`），不做全场统一（`dominant`）—— 工程实测两者差异 <0.01%，按**可读性**选 `own`（玩家能理解"这座火焰塔的共鸣利率取决于我这局在火焰上投了多少"）。

### 5.4 `Stack` 与软 cap

```
Stack_i = Compound_i × Additive_i × Saturating_i          ← 三组之间【串联相乘】

  Compound_i   = 1 + Σ_{c ∈ 复利型卡} gate_c × [ softcap_pow(n_c, 1+κ_c, Cap_i, 1.03) − 1 ]   ← 🔴 组内【并联相加】
  Additive_i   = 1 + Σ_{c ∈ 加法型卡} min(per_layer_c × n_c, cap_c)                            ← 组内相加（逐卡 cap）
  Saturating_i = 1 + Σ_{c ∈ 饱和型卡} cap_c × (1 − e^(−n_c / τ))        τ = 8                  ← 组内相加（饱和）

  softcap_pow(n, k, c, d) = k^n                 (n ≤ c)
                          = k^c × d^(n − c)     (n >  c)
  κ_c   = 该卡所属 Tag 的 κ_tag 档位 − 广度折价（下限 0.02）
  gate_c ∈ {0,1}   ← 条件门，见 §5.4.2
```

> 🔴 **口径红线 R-4（唯一正确读法）**：**复利组内部并联相加，三组之间串联相乘。**
>
> - 复利组**组内**并联（`1 + Σ(m_c − 1)`）= 引擎 `v03/v04/v06` 现行写法（`stack += softcap_pow(...) − 1`）—— 这是**全部定稿数值的扫描基础**，也是防"卡种数 × 层数"双指数的唯一闸门。
> - **组间**串联（复利 × 加法 × 饱和）是为了保住 `card-system` 红线 **C-1「每张单塔效果卡都必须可叠且叠了有用」**：若把加法/饱和卡也并进复利组的求和里，`T2 超频 +80% 攻速` 在终局 `Stack ≈ 13,780` 面前只值 `+0.006%` → **加法/饱和卡在终局集体沦为废卡**。
> - 两条一起看：**深度（层数）是唯一的指数维度，卡种数是线性维度。** 这正是 §1.2 对 P2/P3 的兑现方式。

**MVP 等价性说明（重要，决定要不要复跑）**

| 条件                                                                               | 结论                                                                                |

### 5.4.2 条件门 `CondGate`（冰霜系卡的落地方式）

`card-system` §7.3 的两张冰霜卡带**条件**：T4 凝滞「对**被减速目标**伤害 `×(1+κ)^n`」、T6 霜爆「命中**被减速目标**时溅射」。条件**不新增乘区**，而是在复利项上挂一个**二元门**：

| 项    | 定稿口径                                                                                                 |
| ---- | ---------------------------------------------------------------------------------------------------- |
| 门的形式 | `Compound_i` 中该卡的贡献 × `gate_c`，`gate_c ∈ {0, 1}`。**MVP 二元**，不引入"部分参与率"（那是新数值，且玩家无法直读）                |
| 输入接口 | 战斗层暴露 `TargetStatus.is_slowed(target) → bool`；管线**只读**，不写状态                                          |
| 门不满足 | 贡献 = **0**。🔴 **不报错、不崩、更不得降级为 1.0** —— 否则"冰霜流不配减速源"会白嫖复利，`card-system` §7.3 要的「霜蚀 → 凝滞 → 霜爆」链式协同当场失效 |
| 设计意图 | 让"有没有减速源"成为一个清晰的**布尔决策**：没有 Frost / 霜蚀，凝滞就是废卡 —— 这是冰霜流"条件性高风险高回报"风险画像的机制载体                           |

### 5.5 挂件 `Aux` 乘区

```
slow_eff = max over 挂件塔 j of slow_j            # Frost：0.30 + 0.025 × n_T5(j)，cap 0.60
h_aux    = max over 挂件塔 j of h_j               # 取层数最高的那座（不是求和）
eff_slow = slow_eff × h_aux / (h_aux + 8)         # τ = 8
Aux      = min(1.5, 1 / (1 − min(eff_slow, 0.75)))   # cap 1.5；slow 硬上限 0.75
```

| 构造                                  | `eff_slow`               | `Aux`                           |
| ----------------------------------- | ------------------------ | ------------------------------- |
| 无挂件塔                                | 0                        | `×1.00`                         |
| `Frost(h=1)`，仅自带减速                  | `0.30 × 1/9 = 0.033`     | `×1.035`                        |
| `Frost(h=134)`                      | `0.30 × 134/142 = 0.283` | `×1.395`                        |
| `Frost(h=134)` + T5 满层（`slow=0.60`） | `0.60 × 134/142 = 0.566` | `min(1.5, 2.30) = ×1.50`（撞 cap） |

> 🟡 **Beacon 如何进 `Aux` 未定标**（§9 D-8）：引擎只认 `slow > 0` 的塔 → Beacon（0 减速）当前贡献 0，与 card-system §2.5「Beacon 不会沦为废卡」冲突。**推荐最小改动**：把 Beacon 也计入"挂件塔"，其 `slow_eff` 按 **0.30 等效**计入（语义：信标把减速转化为伤害），与 Frost 共用同一条饱和曲线。备选：Beacon 走独立的并联加法项（需重跑定标）。
