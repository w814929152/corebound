### 1.2 ⚠️ 方法论警告：v2 的「无限购买」口径不能用来校准指数机制

v2 的确定性模型允许玩家**每波把全部积分花光**（实测 W10 单波买入 ~34 层）。
这在实时商店下**不可能**：商品位只有 3 个，刷新受「减速预算 20s/波」限制。
在这个口径下，**任何**指数机制都会溢出到天文数字 —— 
我第一轮跑 `κ_r=0.08` 时多塔 W20 到了 `5.1×10⁸ ×`、起飞提前到 **W4**（直接打破 MVP 验收标准 3 的 W10–15 窗口）。
**那不是 `Resonance` 的强度，是模型的漏洞。**

### 1.5 ⚠️ 我必须重定义判据：「W13–20 持续 ≥8×」这个目标本身是**模型依赖**的

## 2. 复验 1（续）· 塔位 4 → 6 与链接数 `k`（Q10）

### 2.1 MVP 地图能形成的链接数（几何实测）

⚠️ **关键发现：`Rᵢ+Rⱼ` 判据会让链接图饱和成完全图。**
MVP 地图尺寸约 55×55、塔射程 18–22 → `Rᵢ+Rⱼ ≈ 36–44`，几乎任意两塔都满足，
6 塔位下 `k` 直接顶到 5（全互连）。**这样 `k` 就不再是变量，`Resonance` 退化成纯数值 buff，
策划 §2.4.4 想要的「站位拓扑决定复利率」（P1 最硬核的机制化）会失效。**
→ **建议把链接判定收紧为「实质重叠」`d ≤ 0.65·(Rᵢ+Rⱼ)`**，此时 `k` 落在 2–4，
  既保证 `k ≥ 3` 可达（§8.3 要求），又让不同塔位布局产生真实差异。

## 5. 【架构锁定】7 乘区计算管线顺序 —— 交 `damage-pipeline` GDD

### 5.1 先说清楚一件事：纯乘区之间顺序**不影响**结果

7 个都是纯乘法因子，`A×B == B×A`。**锁定顺序的真实目的是另外三件事**：
1. **依赖正确性** —— 有些乘区**读**别的量（层数 / 链接图 / 主塔身份），必须排在写那些量的阶段之后；
2. **浮点确定性** —— 固定顺序 = 同样的输入永远得到同样的 `float`，否则联机/回放/测试会对不上；
3. **未来可维护性** —— 一旦某个乘区从「乘性」改成「加性」或「带夹取」（如 `Empowerment` 的 `slow ≤ 0.75`），
   顺序就从「无所谓」变成「决定结果」。**现在锁死，将来才不会踩雷。**

### 5.2 建议管线（`damage-pipeline` GDD 直接照抄）

| 阶段 | # | 量 | 公式 | 失效/重算触发 |
|---|---|---|---|---|
| 阶段A | A1 | CoverageScore_i | 几何：slot_i 射程覆盖路径长度占比 | 塔位/建塔/拆塔 |
| 阶段A | A2 | LinkGraph | 几何：dist(slot_i,slot_j) ≤ f·(R_i+R_j) | 塔位/建塔/拆塔 |
| 阶段A | A3 | h_i（塔卡层数） | 该塔实例被投入的塔卡层数 | 买塔卡 |
| 阶段A | A4 | L_i（装配层数） | 装配到该塔的强化卡层数之和 | 买强化卡/改装配 |
| 阶段A | A5 | CoreTower | argmax L_i（涌现，非声明） | A4 变化 |
| 阶段A | A6 | TagTier | 每 Tag 投入层数 → (κ, StackCap) 档位 | 买卡 |
| 阶段B | B1 | Base_i | TowerDPS(type) × h_i^0.6（次线性） | A3 |
| 阶段B | B2 | ★Stack 复利 | 1 + Σ_r [softcap_pow(1+κ_tag, L_r) − 1] | A4/A6 |
| 阶段B | B3 | Tag 协同 Syn_i | ×1.5（该 Tag 塔卡层数 ≥ 3） | A3（现为一次性乘区，v0.3 拟改为档位 → 并入 B2） |
| 阶段B | B4 | ★Resonance | (1+κ_r)^{E_i}，E_i = Σ_{j∈N(i)}(1+h_j) | A2/A3 |
| 阶段B | B5 | ★Focus | 1 + 0.15 × L_i | A4 |
| 阶段B | B6 | ★AllIn | ×1.6（i==CoreTower 且 L_i ≥ 60%·ΣL） | A4/A5 |
| 阶段B | B7 | Coverage_i | A1 | A1 |
| 阶段C | C1 | AoE 密度效率 | min(cap, 1+per·Σh_tagged) | A3 |
| 阶段C | C2 | ★Crossfire | ≥3 塔覆盖 ×1.5；≥2 塔 ×1.25 | A1/A2 |
| 阶段C | C3 | ★挂件 Aux | Π 1/(1−slow_k) × Π(1+aura) | 挂件塔存在 |
| 阶段C | C4 | ★Empowerment | 挂件减益随 CoreTower 层数（T1） | A4/A5 |

```
每波开始（或塔位/建塔/拆塔/改装配 时）→ 重算 阶段A

Raw_i  = Base_i                      # B1
       × Stack_i                     # B2  复利引擎① 深度
       × Syn_i                       # B3  （v0.3 拟并入 B2 的档位）
       × Resonance_i                 # B4  复利引擎② 广度
       × Focus_i                     # B5
       × AllIn_i                     # B6
       × Coverage_i                  # B7

Delivered = ( Σ_i Raw_i )            # C0 逐塔求和
          × AoE密度效率               # C1
          × Crossfire                # C2
          × Aux(挂件)                 # C3
          × Empowerment              # C4（T1）
```

**四个真正不可交换的依赖（这才是要锁的东西）**：
| 依赖 | 说明 | 违反后果 |
|---|---|---|
| `B2 Stack` ← `A6 TagTier` | 复利率 κ 与软 cap 由 Tag 档位决定 | 档位没算就取不到正确 κ |
| `B6 AllIn` ← `A4 L_i` + `A5 CoreTower` | 主塔身份与层数占比 | 主塔判错 → 单核流吃不到 ×1.6 |
| `B4 Resonance` ← `A2 LinkGraph` + `A3 h_j` | 链接图与**邻居**的塔卡层数 | **塔位没变但 h 变了也要重算** |
| `C4 Empowerment` ← `A4 CoreTower 层数` | 挂件减益随主塔层数 | T1 落地时最易漏 |

### 5.3 🔴 三个必须写进 GDD 的实现陷阱

1. **`Resonance` 是「邻居」乘区，塔自己不吃自己的层数。**
   `E_i = Σ_{j∈N(i)} (1+h_j)` 中的 `j` **不含 `i`**。塔 j 的塔卡层数只喂给**别人**。
   → 实现里若写成 `Σ_all(1+h)` 会把每塔倍率抬高 `(1+κ_r)^{1+h_i}` 倍，**数学上与模拟完全对不上**。
   → 且这意味着：**单塔无链接时 Resonance 恒等于 1.0**，必须显式写这条边界。
2. **所有乘区必须缓存，且失效粒度要分清。**
   `CoverageScore` / `LinkGraph` 只在**塔位变动**时重算（建塔/拆塔/塔位改动）—— 每帧算会炸。
   `Stack/Focus/AllIn` 在**改装配**时重算。
   `Resonance` 在**链接图变动 或 任一邻居的 h 变动**时重算 —— 
   ⚠️ 注意这里：买一张塔卡会同时触发 `h_j +1` **和** 所有邻居的 `E_i` 重算，这是最容易漏的失效路径。
3. **`Stack` 的软 cap 必须在乘区**内部**夹取，不能在外面。**
   `softcap_pow(lv) = κ^min(lv,cap) · decay^max(0, lv-cap)`。
   若在乘区外部做 `min(mult, cap_value)`，`decay` 分段就失效了。

## 7. Godot 4 实现方案评估（`Resonance` 的架构层新增依赖）

### 7.1 链接图：不要每帧算，用「事件驱动 + 脏标记」

```gdscript
# autoload: ResonanceGraph.gd
var _towers: Array[Tower] = []
var _adj: Array[Array] = []      # 邻接表，索引与 _towers 对齐
var _dirty := true

func mark_link_dirty() -> void:  _dirty = true

func _physics_process(_dt: float) -> void:
    if not _dirty: return
    _rebuild()          # O(n^2)，n<=8，实测 <0.05ms
    _dirty = false

func _rebuild() -> void:
    var n := _towers.size()
    _adj = []; _adj.resize(n)
    for i in n:
        _adj[i] = []
        for j in n:
            if i == j: continue
            var d := _towers[i].global_position.distance_to(_towers[j].global_position)
            if d <= LINK_FRAC * (_towers[i].range + _towers[j].range):
                _adj[i].append(j)   # ★ 不含 i 自己 —— 见 §5.3 陷阱 1
```

**失效触发点（三个，缺一即出 bug）**：
1. `tower_placed(slot)` / `tower_removed(slot)` → `mark_link_dirty()`
2. `tower_range_changed`（塔升级改射程 / 光环 buff）→ `mark_link_dirty()`
3. `tower_level_changed`（**塔卡层数 h 变化**）→ 不重建拓扑，但**必须**让邻居的 `E_i` 失效 →
   用 `E_dirty` 脏标记而不是重建邻接表（拓扑没变，只有权重变了）。

### 7.2 数值范围：必须防溢出

`(1+κ_r)^{E_i}` 在 `E_i` 到 300 量级时就是 `1e10`。**建议**：
- 伤害值在管线内部用 `float`（Godot `float` = double，`1e308` 上限，20 波内安全）；
- 但**显示层必须走 `log10` 缩写**（K/M/B/T…），且 `DamageNumber` 组件在 `>1e6` 时切换科学计数；
- **存档 / 联机同步用「层数」而不是「伤害值」** —— 层数是有界小整数，伤害值不是。
  （MVP 无存档无联机，但这条现在定下能省掉 T2 的重构。）

### 7.3 性能预算

| 项 | 量级 | 评估 |
|---|---|---|
| 链接重建 | O(n²), n ≤ 8 | < 0.05 ms，且只在事件后一帧发生 → **可忽略** |
| 每塔伤害求值 | 7 乘区 × n | < 0.01 ms → **可忽略** |
| 链接可视化 | ≤ 15 条光弧 | 用 `Line2D`/`Polyline2D` + 一条共享 `ShaderMaterial`，**禁止每塔一个 Material** |
| 🔴 真瓶颈 | **伤害数字 + 弹幕** | `Resonance` 让后期 DPS 到 1e8+ → 命中事件频率会打爆 UI。**必须做伤害数字合并（同目标 100ms 内聚合）**，否则帧率崩在 UI 而不是在伤害管线 |

### 7.4 与「战术减速 0.35×」的交互（横切关注点）

`Resonance` 的重算是事件驱动的，**与 `Engine.time_scale` 无关** —— 这一点必须在 GDD 里写死。
风险点：若把链接重建放进 `_process` + 计时器，减速时会跟着变慢甚至漏帧。
**建议**：链接图与伤害管线全部走**不受 `time_scale` 影响的路径**（`_physics_process` 且用 `Engine.get_physics_interpolation_fraction()` 之外的真实 dt，或直接事件驱动不依赖帧）。

## 8. 本轮遗留（诚实标注）

1. **覆盖率模型未统一**：本报告沿用 v2 的「路径聚合覆盖」（A 0.78 / B 0.95）。
   我试过切换到**逐塔几何覆盖**，结果两条路径都无法起飞（单塔覆盖率只有 0.2–0.5，v2 的 0.95 是「塔网合计」而非「单塔」）。
