## 0. 一页速览（Vision in One Page）

| 维度 | 定调 |
|---|---|
| 一句话风格 | **「厚描边卡通低模」**——3D 低多边形体块 + 卡通分层着色 + 全物体黑色描边，观感贴近 2D 手绘等距，生产成本贴近 2D 的十分之一 |
| 气质拼接 | 《王国保卫战》的**塔防清晰度** + 《小丑牌》的**卡牌/数值爽感** + 《吸血鬼幸存者》的**同屏洪流与滚雪球** |
| 视觉第一原则 | **任何一帧截图暂停后，玩家能在 1 秒内分清「我 / 敌 / 可交互物」**——后期百怪同屏时这条压倒一切美观考量 |
| 第二原则 | **反馈必须随数值升级**：玩家变强时，画面的"音量"也要变大。这是本作爽点的视觉载体 |
| Solo 约束 | 优先**程序化动画**（Tween/Shader）与**材质色着色**，尽量不依赖骨骼动画与手绘贴图 |

## 1. 整体美术风格（Art Style）

### 1.1 方向定位

**主方案：Low-Poly 3D + Toon/Cel 分层着色（"3D 体块，2D 观感"）**

- 场景与单位为**真 3D 低模**，但使用正交等距相机 + 卡通材质，最终观感接近 2D 插画等距。
- 选它的理由（Solo 快迭代优先）：
  1. Godot 4 的 3D 管线**免费解决深度排序**——等距 2D 项目最痛的 y-sort 问题直接消失。
  2. 一个模型可从任意角度复用、缩放、旋转、换色，怪物种类扩张成本远低于逐帧 2D。
  3. 低模可用程序化生成/形变快速做变体（同一骨架换头换色换比例 = 新怪）。
  4. 数量爆炸时，3D 实例化渲染（MultiMesh / GPU 粒子）性能天花板更高。
- **UI 与卡牌走纯 2D**：场景 3D + UI 2D 的混合管线，卡牌插画使用扁平矢量/厚描边插画风，与 3D 卡通描边语言保持一致。

### 1.2 参考板（Reference Board）

| 参考对象 | 借什么 | 不借什么 |
|---|---|---|
| 《Kingdom Rush》 | 单位剪影辨识度、厚描边、塔的"玩具感"、命中反馈的干脆 | 其写实贴图与高细节度 |
| 《Balatro》 | 卡牌的物理质感（倾斜/抬起/弹跳）、数值字体排版、连击时的夸张数字演出 | 其纯 2D 像素表现 |
| 《Vampire Survivors》 | 同屏数量管理、伤害数字洪流、数值爆炸的失控感 | 其像素颗粒感与低分辨率 |
| 《Brotato》 | 极多敌人下的可读性处理（投影、描边、击退分离） | 其简陋感 |
| 《Bad North》 | 极简等距低模、干净的地形块面、柔和配色 | 其极低饱和度 |
| 《Into the Breach》 | 等距网格的绝对清晰、信息零歧义 | 其硬科幻题材 |

### 1.3 风格红线（明确不做）

- ❌ 写实 PBR、高精度法线细节、真实比例——成本与 Solo 产能不匹配。
- ❌ 纯像素等距——卡牌 UI 与像素风混搭会撕裂，且瓦片-单位对齐成本高。
- ❌ 暗色糊成一团的"写实暗黑风"——本作需要百怪同屏仍可读，暗色低对比是自杀。
- ❌ 无描边的柔和渲染——描边是本作可读性的生命线，不可省。

## 2. 配色方案（Color Palette）

### 2.1 核心原则：**青 / 橙 双极对立**

全场只存在两个"阵营色极"，所有配色围绕它们组织：

- **玩家极 = 冷（青蓝 Cyan）**：中心防御塔、友方投射物、可建造范围、增益光环。
- **敌人极 = 暖（橙红 Orange）**：怪物、敌方投射物、来袭路径、威胁标记。

> 为什么是青 vs 橙：这是**红绿色盲（Deutan / Protan）下仍然可分的色对**（蓝-黄轴），同时天然符合"冷=后方/安全，暖=前方/危险"的直觉。颜色是**第一编码**，形状是**第二编码**（见 §3）。

卡牌稀有度采用**高饱和、明度递增**的五级色，保证在深色店铺背景上一眼可辨：

### 2.4 波次 / 危险等级色彩语言（环境换装）

每 5 波做一次**环境色调迁移**，给玩家"我在推进"的进程感，同时用暖化暗示威胁升级：

| 波次区间 | 主题 | 环境雾色 | 主光色 | 附加 |
|---|---|---|---|---|
| 1–5 | 晨雾 | `#2A3550` | `#FFF3E0` 暖白 | 无 |
| 6–10 | 黄昏 | `#4A2E52` | `#FFD9A8` 橙白 | 地面长投影 |
| 11–15 | 血夜 | `#5A1E32` | `#FFB6A0` 赤白 | 边缘红光缓慢脉冲 |
| 16+ | 虚空 | `#2A1240` | `#D8C0FF` 紫白 | 星屑粒子缓慢飘落 |
| Boss 波 | — | 沿用当前 | 压暗 20% | 上下黑边（Letterbox）+ 地面符文亮起 |

迁移用 **3 秒缓动过渡**，不得突变（突变会造成视觉惊吓与可访问性风险）。

## 3. 形状语言（Shape Language）

### 3.1 阵营形状对立（第二编码）

| 属性 | 玩家侧（塔/友方） | 敌人侧（怪物/敌弹） |
|---|---|---|
| 轮廓走向 | **垂直向上**、重心高、塔状/柱状 | **水平前倾**、重心低、团状/爬伏 |
| 对称性 | **严格对称**（旋转对称 4 或 8 次） | **不对称**（左右不等、倾斜） |
| 基础几何 | 方、八棱柱、正三角尖顶 | 圆球 + 不规则尖刺、液滴、破块 |
| 边缘 | 直线、硬折角、整齐层叠 | 曲线、锯齿、参差破损 |
| 底座环 | **规则八边形环**（青） | **不规则裂环/尖刺环**（橙） |
| 运动 | 原地旋转/缩放，位移克制 | 扭曲、挤压拉伸（squash & stretch）、摆动前进 |
| 一句话 | **"人工、稳定、向上"** | **"生物、混乱、扑来"** |

### 3.2 剪影辨识度规则（强制）

1. **缩略图测试**：任何新单位/建筑，导出 64×64 纯黑剪影 PNG，在深色背景并列展示，必须能被正确归入「我方 / 敌方」——通不过即打回重做。
2. **禁止撞形**：敌我双方不得使用相近的基本几何体（例如玩家塔不得是球体，怪物不得是规整八棱柱）。
3. **体量分层**：同屏单位按体型分三层，层间高度差 ≥ 40%：
   - 杂兵：矮（0.6 单位高）、宽 0.5
   - 精英：中（1.2 单位高）、宽 0.8
   - Boss：高（2.5 单位高）、宽 2.0，且**必须有独特顶部轮廓**（角/翼/单眼等）
4. **底部投影（Blob Shadow）**：所有单位强制投射一个椭圆软阴影，用于把单位"钉"在地面上，避免等距视角下的漂浮感与位置歧义。
5. **描边（Outline）强制**：所有 3D 单位使用外扩背面描边（Inverted Hull），颜色为**极深色而非纯黑**（塔用 `#0E2430`，怪用 `#2E1008`），保持与本体色的关联。

### 3.3 投射物形状

- 友方投射物：**细长梭形/箭形**，尖端朝飞行方向，带一条渐隐尾迹（青）。
- 敌方投射物：**圆球/液滴/不规则碎块**，体积更大、速度更慢、带拖尾粒子（橙）。
- 判定：任何投射物在最小尺寸下，其**长宽比 ≥ 2:1 = 友方，≈ 1:1 = 敌方**。

### 3.4 UI 卡牌形状

- 统一 **1:1.4 竖版圆角矩形**，圆角半径 = 宽的 6%。
- 顶部为插图区（正方形），底部为文字区。稀有度越高，卡面装饰越多（角饰、底纹、外框厚度）。
- 卡牌在牌组中**轻微扇形堆叠**，在商店中**平铺一行**，两种状态用不同倾斜角区分（牌组 -3°，商店 0°）。

## 4. 光影与材质（Lighting & Material）

### 4.1 统一光照（等距视角的生死线）

**全场景只允许一盏方向光作为造型光，朝向必须全局统一。**

| 参数 | 值 | 说明 |
|---|---|---|
| 主光方位 | 屏幕**左上**（相机空间 -45°） | 等距惯例：光从左上打，法线朝上的面最亮 |
| 主光俯角 | **50°** | 兼顾顶面亮度与侧面塑造 |
| 主光色/强度 | `#FFF3E0` / 1.0 | 暖白，随波次换装 |
| 环境光（天光） | `#5A6BFF` / 0.25 | 冷色补暗部，建立冷暖对比 |
| 地面反弹光 | `#2A3550` / 0.12 | 极弱，仅防死黑 |
| 阴影 | 硬边阴影 + 单位底部 blob 阴影双轨 | 硬边强化卡通感；blob 保证落地感 |

> ⚠️ **禁止**：任何单位自带不同方向的假光照（贴图里画死的高光方向错误会让整体散架）。若用贴图，所有贴图的光向必须一致。

### 4.2 材质规范

- **Toon / Cel Ramp 三阶着色**：暗部 → 基色 → 亮部，硬过渡（smoothness ≈ 0.08）。不使用 PBR 金属/粗糙度流程。
- **首选材质色 + 顶点色**：低模尽量用纯色材质 / 顶点色上色，**不依赖手绘贴图**（Solo 友好、体量轻、换色只需改参数）。
- 需要贴图时（Boss、特殊地形）：单张 **512×512** 手绘/生成贴图，风格为"平涂 + 单条硬边阴影"，禁止渐变与写实纹理。
- **Rim Light（边缘光）**：所有单位加一圈阵营色边缘光（玩家青 / 敌人橙），强度 0.6。这是同屏混乱时**分离相邻单位**的关键手段。
- **描边**：Inverted Hull，屏幕空间恒定宽度（约 2px @1080p），保证远处单位不被糊掉。

### 4.3 后期处理栈（Post-Processing Stack）

按序叠加，全部可在设置中按档位关闭（见 §9）：

1. **Bloom** — 阈值 0.85（只吃高亮热色），强度 0.6。数值爆炸时动态提升至 1.6。
2. **Vignette** — 强度 0.3，柔和。
3. **色调映射** — Filmic 或 ACES（保留高光滚降，让爆炸不过曝成一团白）。
4. **色差（Chromatic Aberration）** — 平时 0，仅在超载状态短暂启用（0.3 强度，0.2s）。
5. **径向模糊** — 仅 Boss 死亡 / 超载触发瞬间，0.25s，强度 0.4。
6. **屏幕震动** — 见 §8.4 分级表。
7. **轻微景深** — 可选，等距下收益低，**默认关闭**。

### 4.4 数值爆炸时的屏幕反馈（Occupancy）

"数值爆炸"不是加更多粒子，而是**整体画面参数的短时跃迁**：

| 项 | 常规 | 超载峰值 |
|---|---|---|
| Bloom 强度 | 0.6 | 1.6 |
| 曝光（Exposure） | 1.0 | 1.25 |
| 饱和度 | 1.0 | 1.3 |
| 屏幕边缘能量框 | 无 | 阵营金色/彩虹脉冲边框 |
| 色差 | 0 | 0.3 |
| 时间缩放 | 1.0 | 0.35（仅超规格击杀，≤0.4s） |

所有跃迁走 **0.15s 上升 / 0.5s 回落**的包络，避免持续刺眼。

## 5. UI / UX 视觉方向（UI Visual Direction）

### 5.1 总体风格

与 3D 场景同语言：**厚描边 + 高饱和平涂 + 微立体**。参考《Balatro》的"实体感卡牌"——UI 元素不是贴片，而是有重量、会弹跳的物件。

- 所有主要面板：深色底（`#141726` @ 92% 不透明）+ 3px 亮色描边 + 内部 1px 分隔线。
- 按钮/卡牌：默认微下沉，悬停**抬起 4px + 缩放 1.05 + 倾斜 2°**，点击**下压 + 缩放 0.97**，全程 0.12s 弹性缓动。
- 禁止使用系统默认控件；所有控件为自定义 Control 节点。

### 5.2 信息层级原则

**数字 > 图标 > 文字 > 装饰。** 玩家在后期不会读文字，只会扫数字。

| 层级 | 内容 | 字号 @1080p | 字重 | 颜色 |
|---|---|---|---|---|
| L0 关键 | 积分、基地血量、波次倒计时 | 48–64px | Black | 辉金 / 警报红 |
| L1 重要 | 卡牌费用、伤害数值、升级选项标题 | 28–36px | Bold | 白 / 稀有度色 |
| L2 常规 | 卡牌描述、状态说明 | 18–20px | Medium | `#C8CFDA` |
| L3 辅助 | 提示、tooltip、版本号 | 14–16px | Regular | `#8B94A5` |

- **数字必须等宽（Tabular）**，避免滚动时抖动。
- 积分变化时：**数字滚动 + 缩放脉冲 + 金色粒子**，0.3s。
- 伤害数字：见 §8.3 分级表。

### 5.3 核心界面视觉

| 界面 | 视觉要点 |
|---|---|
| **商店（卡牌区）** | 底部横向展开面板，占屏 1/3 高；卡牌平铺 3–5 张，未选中的降饱和 60% + 缩小 0.9；"刷新"按钮置于右侧，使用**辉金**色并带循环微光，暗示"可以一直刷" |
| **升级 / 构筑面板** | 全屏半透明遮罩 + 三选一卡片居中扇形展开，入场逐张弹入（间隔 0.08s） |
| **卡组 / 已购卡牌** | 左侧可收起抽屉，卡牌小尺寸网格排列，稀有度色边框 + 数量角标 |
| **HUD · 积分** | 左上角，辉金大字 + 硬币图标，变化时跳动 |
| **HUD · 基地血量** | 屏幕底部中央，横向分段血条（每段 = 1 点），受击时该段闪红并碎裂 |
| **HUD · 波次** | 顶部中央，波次号 + 进度条 + 下一波倒计时；Boss 波切换为红色警示条 |
| **波次提示** | 波次开始前 2 秒，屏幕中央大字 "WAVE 7" 由大缩小落下 + 屏幕边缘光扫过，1.2s 后淡出 |

### 5.4 字体

- **展示/数字字体**：一款粗壮高冲击的无衬线 Black 字重（候选：Fredoka / Balatro 风格圆厚体 / Poppins Black）。
- **正文字体**：中性无衬线（Inter / Roboto）。
- **中文**：思源黑体（Source Han Sans）Bold / Medium，需与拉丁字体做 x-height 对齐。
- **许可注意**：上线前确认字体商用授权，优先 SIL OFL 字体。

## 6. 资产规格（Asset Specs）

### 6.1 等距瓦片与相机

| 项 | 规格 |
|---|---|
| 逻辑瓦片尺寸 | **1 × 1 world unit** |
| 相机投影 | Orthogonal（正交） |
| 相机旋转 | `rotation_degrees = (-30, 45, 0)`，`rotation_order = YXZ` → **经典 2:1 菱形瓦片** |
| 备用 | `(-35.264, 45, 0)` = 真等距（√3:1），更"正统"但屏幕利用率略低 |
| 相机 size | **6.0** → 1080p 下 ≈ 90 px/unit，瓦片屏幕尺寸 ≈ **128 × 64 px** |
| 1080p 可视范围 | ≈ 21.3 × 12 world units（约 15 × 17 个瓦片菱形） |
| 竞技场建议尺寸 | **24 × 24 瓦片**（可视范围内可容纳包围感），相机固定不跟随 |

### 6.2 3D 模型预算（三角面）

| 类别 | 预算 | 备注 |
|---|---|---|
| 地形瓦片块 | 8–40 tri | 用简单块面拼装，非整块地面 |
| 场景道具（石/树/柱） | 100–400 tri | |

## 7. 2.5D 等距规范（Isometric Specs）

### 7.1 网格与坐标

- 世界空间：XZ 平面为地面，Y 为高度。1 unit = 1 瓦片。
- 瓦片坐标用 `Vector2i(x, z)`，中心点世界坐标 = `(x + 0.5, 0, z + 0.5)`（瓦片原点在角上）。
- 相机固定、不旋转、不做自由缩放（只允许 ±10% 的演出性推拉）。

### 7.2 深度排序规则

**3D 场景由深度缓冲自动处理**，仅需约定以下几条：

1. **不透明物体**：全部写入深度，无需手工排序。✅
2. **半透明 / 粒子 VFX**：`transparent = true`，`depth_draw = NEVER`，用 `render_priority` 手工指定层级：
   - 地面贴花 = 0
   - 单位脚下的地面光环 = 1
   - 单位本体特效 = 2
   - 投射物尾迹 = 3
   - 爆炸 / 伤害数字 = 4（最上层）
3. **地面贴花（Decal）**：贴地物件 Y 轴抬高 `+0.01`，消除 z-fighting。
4. **伤害数字**：使用 3D → 2D 投影的 CanvasLayer 文字，跟随世界坐标，始终置于所有 3D 之上。
5. **禁止**半透明物体使用 `depth_draw = ALWAYS`（会互相切割，产生闪烁）。

### 7.3 单位占位规范

单位使用**圆形碰撞半径**（不是瓦片对齐），允许自由走动，但渲染需遵守：

| 类型 | 碰撞半径 | 视觉体宽 | 备注 |
|---|---|---|---|
| 杂兵 | 0.22 | ≤ 0.5 | |
| 精英 | 0.35 | ≤ 0.8 | |
| Boss | 0.9 | ≤ 2.0 | |
| 防御塔 | 0.5（1 格） | ≤ 0.9 | 塔固定占完整 1 格，中心对齐格心 |

- **防堆叠（关键）**：所有单位启用**分离力（Separation）**，保证任意两单位中心距 ≥ 两者半径和的 85%。后期糊成一团是本作可读性的头号杀手。
- 单位脚底必须与地面接触点对齐（模型原点在脚底中心，不在几何中心）。
- 塔的占位格在地面上以**青色半透明菱形**高亮，敌方来袭路径以**橙色箭头贴花**标示。

### 7.4 高度与遮挡

- 场景高度上限 **4 单位**；超过会遮挡后排，一律禁止。
- 高物体（Boss、满级塔）需做**遮挡淡出**：当它挡住玩家单位时，轮廓以 0.35 透明度显示剪影（可选，Phase 2 实现）。

## 8. VFX / 反馈原则（VFX & Juice）

> 本节是本作爽点的核心。设计目标：**让玩家"看见"自己在变强。**

### 8.1 四层反馈模型

| 层 | 触发 | 表现 | 时长 |
|---|---|---|---|
| **L1 微观** | 单次命中 | 受击体闪白 1–2 帧 + 伤害数字弹出 + 3–6 粒火花 + 微击退位移 | 0.1s |
| **L2 中观** | 击杀 | 单位爆散为阵营色碎片 + 地面冲击环 + 掉落物弹出；精英/Boss 加 **hitstop 40–80ms** | 0.3s |
| **L3 宏观** | 购买/升级 | 卡牌飞向牌组带金色拖尾 + 塔升级光柱 + 全屏边缘光脉冲一次 + UI 弹跳 | 0.6s |
| **L4 超宏观** | **Build 成型 / 数值爆炸** | 见 §8.4「超载 Overload」 | 持续 |

### 8.2 Juice 随数值升级（核心机制）

**同一动作的反馈强度必须随玩家当前数值增长。** 玩家 1 级和 30 级杀死同一只杂兵，演出必须不同。

| 指标 | 弱（早期） | 中 | 强（后期） |
|---|---|---|---|
| 命中火花粒子数 | 3 | 8 | 16 |
| 击杀碎片数 | 5 | 12 | 24 |
| 击退距离 | 0.05 | 0.15 | 0.35 |
| 冲击环半径 | 0.5 | 1.0 | 2.0 |
| 屏幕震动 | 无 | 1 级 | 3 级 |
| hitstop | 无 | 40ms | 80ms（仅精英/Boss） |

实现方式：定义一个全局 `JuiceScale`（由玩家 DPS / 连击 / 当前波次推导，0–1），所有 VFX 参数乘以 `1 + JuiceScale * k`。

### 8.3 伤害数字分级表（Visual Damage Tiers）

| 单次伤害占目标最大血量 | 字号倍率 | 颜色 | 动画 |
|---|---|---|---|
| < 10% | 1.0× | 白 `#FFFFFF` | 上浮 + 淡出 |
| 10–30% | 1.3× | 淡金 `#FFE38A` | 弹出 + 轻微缩放 |
| 30–60% | 1.7× | 辉金 `#FFC94A` | 弹出 + 旋转抖动 |
| 60–100% | 2.2× | 橙金 `#FF8A2B` | 弹出 + 冲击环 + 1 级震屏 |
| **超杀 / 溢出** | **3.0×** | **彩虹流光** | 弹出 + 全屏色差 + 慢动作 0.35×（0.4s，冷却 3s） |

**同屏数字上限 40 个**，超出时合并为聚合数字（"×127"）并升级一档表现，防止刷屏与性能崩塌。

### 8.4 超载状态（Overload）—— 核心爽点演出

**触发条件**（任一满足）：单秒击杀数 ≥ 阈值 / 连击 ≥ 25 / 单帧总伤害 ≥ 阈值 / 玩家 DPS 突破里程碑。

**进入演出（0.4s）**：
1. 时间缩放降至 0.35×（0.4s 内回升）
2. Bloom 0.6 → 1.6，曝光 1.0 → 1.25，饱和度 1.0 → 1.3
3. 屏幕四边亮起**金色能量边框**，向中心脉冲
4. 低频"充能"音效起（阮和鸣负责）

**持续状态（可维持数秒）**：
- 所有伤害数字 +1 档表现，颜色向彩虹偏移
- 敌人死亡改为**连锁爆散**（每只死亡触发周围小范围冲击）
- 击杀连击计数器（Combo）居中显示，每 10 连击跳一次字
- 背景雾色向暖金偏移，地面出现能量裂纹贴花
- 屏幕震动维持 1–2 级（低频、柔和）

**退出（0.6s 回落）**：所有参数缓动回常规，边框能量向内收束消散，留一次轻微余震。

> ⚠️ **冷却与上限**：超载触发冷却 ≥ 6s，持续上限 8s。目的是让"爆炸"成为**稀缺的高光时刻**，而不是常态噪音。常态噪音 = 玩家脱敏 = 爽点失效。

### 8.5 防过载与性能护栏

| 护栏 | 值 |
|---|---|
| 同屏活跃粒子系统上限 | 48 |
| 单粒子系统最大粒子数 | 64（普通）/ 256（Boss） |
| 同屏投射物上限 | 300（超出转为光束/链式表现） |
| 同屏伤害数字上限 | 40（聚合升级） |
| 屏幕震动等级上限 | 5 级，且设置中可关闭 |
| 慢动作触发冷却 | 3s |
| 目标帧率 | 1080p / 60fps（中端 GPU）；掉到 45fps 时自动降一档粒子预算 |

所有 VFX 必须**对象池化**，禁止运行时 instantiate。

### 9.2 强制红线（不可妥协）

1. **任何游戏状态不得仅靠颜色传达。**（P0）

3. **屏幕震动必须可关闭。**（P0，晕动症）
4. **正文文本对比度 ≥ 4.5:1。**（P0）

### 9.3 后续等级规划（不在本阶段实现）

- **Standard**：UI 完全重映射、色盲模拟实时预览、字幕系统完整化、文本朗读。
- **Comprehensive**：全键位重映射、辅助难度选项、单手模式、自定义色板。

> 📌 UX 规格（由文策渊产出）**必须引用本分级**：所有界面设计需满足 Basic 级 P0 项。
